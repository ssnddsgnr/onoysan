# 1. Философия: Разрыв Идентичности (Identity Split)

В архитектуре Sana мы реализуем принцип радикального разделения данных. Финансовое ядро (Ledger) не должно знать, кто такой пользователь в реальном мире.

**Layer 1 (Public Overlay):** Знает Telegram ID, Email, Никнеймы и Аватары. Занимается маршрутизацией сообщений и поиском пользователей.

**Layer 2 (Private Core):** Знает только анонимный `internal_user_id` (UUID). Хранит деньги, транзакции и цели. **Главный инвариант:** Таблицы финансового реестра (`ledger_transactions`, `wallets`) **никогда** не содержат полей `telegram_id`, `email` или `phone`.


--------------------------------------------------------------------------------

# 2. Слой Аутентификации: Шлюз (Gateway)

Таблица `auth_identities` является единственным мостом между внешним провайдером и внутренней системой.

## 2.1. Схема связки (`auth_identities`)

Это «прихожая» системы. Здесь внешний паспорт меняется на внутренний пропуск.

| Поле | Описание | Логика Безопасности |
| --- | --- | --- |
| internal_user_id | UUID (Master Key) | Единственный ключ, используемый в Ledger. Один пользователь может иметь несколько методов входа (TG + Email). |
| provider_type | Enum (telegram, email) | Тип внешнего идентификатора. |
| external_id | VARCHAR (Encrypted) | Реальный ID (Telegram ID 123456). Хранится в зашифрованном виде (Encryption at Rest) для обратной маршрутизации сообщений. |
| identity_hash | VARCHAR (Hash) | Хэш внешнего ID (Argon2/SHA-256). Используется для быстрого поиска (SELECT WHERE identity_hash = ...) без дешифровки external_id при каждом запросе. |
| status | Enum (active, blocked) | Позволяет мгновенно отключить вход через конкретный соц. канал, не удаляя финансовые данные. |

## 2.2. Процесс входа (Auth Flow)

**Ingestion:** Бэкенд получает Update от Telegram с `tg_id: 999888`.

**Lookup:** Бэкенд вычисляет хэш от `tg_id` и ищет его в `identity_hash`.

**Token Exchange:** Если найдено — выдает JWT-токен, содержащий `internal_user_id`.

**Context Injection:** С этого момента вся работа идет только с `internal_user_id`. Исходный `tg_id` стирается из памяти процесса обработки.

# 3. Социальный Оверлей: Никнеймы и Профили

Для реализации функций совместного доступа (Shared Sovereignty) и командной работы пользователям нужно находить друг друга, не обмениваясь длинными UUID. Для этого вводится **Социальный Оверлей** поверх таблицы `users_metadata`.

## 3.1. Публичный профиль (`users_metadata`)

Эта таблица хранит атрибуты, по которым пользователя могут найти другие люди.

| Поле | Описание | Видимость |
| --- | --- | --- |
| internal_user_id | PK | Скрыт. |
| nickname | Unique Index. Уникальное имя (напр. @alex_finance). | Публичное. Основной инструмент поиска и меншенов. |
| encrypted_display_name | Имя (напр. «Алексей»). | Приватное. Видит только сам пользователь и его ИИ-ассистент. |
| avatar_url | Ссылка на картинку. | Публичное (для доверенных контактов). |
| is_discoverable | Boolean. | Если false, пользователя нельзя найти по никнейму (режим «Stealth»). |

## 3.2. Логика «Командной Магии» (Social Discovery)

Когда пользователь хочет добавить партнера в бюджет или отправить запрос на средства:

**Запрос:** Пользователь пишет: *«Добавь @maria_k в проект Отпуск»*.

**Resolution:** Дирижёр обращается к Бэкенду.

**Lookup:** Бэкенд ищет `nickname = 'maria_k'` в `users_metadata` и возвращает `internal_user_id`.

**Grant:** Создается запись в `access_grants` для найденного UUID. Реальные имена и Telegram ID в процессе не раскрываются.

# 4. Управление множественными идентичностями

Система поддерживает связывание нескольких методов входа в один профиль, что обеспечивает отказоустойчивость доступа.

## 4.1. Сценарий: Миграция и Резервирование

**Проблема:** Telegram-аккаунт угнан или удален.

**Решение:** Пользователь может заранее привязать Email. В таблице `auth_identities` появится вторая строка с тем же `internal_user_id`, но `provider_type = 'email'`.

**Результат:** Финансовая история (Ledger) не привязана жестко к Telegram. Это делает пользователя суверенным от платформы мессенджера.

## 4.2. Авто-обогащение (Auto-Enrichment)

При первом входе через Telegram, система автоматически извлекает публичный `username` и предлагает использовать его как `nickname` в Sana, упрощая онбординг. Пользователь может изменить его позже, но `external_id` (Telegram ID) останется неизменным ключом в подвале системы, пока не будет изменён подтверждением через почту.

# 5. Приватность и AI-Цензура

AI-слой (Дирижёр и Агенты) работает в условиях строгого карантина информации о личности.

## 5.1. AI Sanitization Protocol

Когда Бэкенд формирует контекст для LLM:

**Разрешено:** `internal_user_id` (для поиска в векторе), `nickname` (для обращения), расшифрованное `display_name` (для приветствия "Привет, Алекс").

**Запрещено:** `external_id` (Telegram ID), `email`, `phone`. Эти поля физически не выбираются из БД при запросах для генерации промптов.

## 5.2. Hashing Strategy

Для обеспечения безопасности даже в случае дампа базы данных `auth_identities`:

Поле `external_id` зашифровано симметричным ключом (хранится в Vault), чтобы Бэкенд мог *отправлять* ответы пользователю.

Поле `identity_hash` используется для *входа*. Оно необратимо. Злоумышленник, получив базу, не сможет массово сопоставить кошельки с реальными Telegram-аккаунтами, не имея ключей шифрования.

# Резюме

Модуль **Identity-Social-Overlay** создает защищенную прослойку. Снаружи — удобные никнеймы и привычный вход через Telegram. Внутри — строгая анонимность UUID. Бэкенд прозрачно транслирует одно в другое, гарантируя, что «социальность» не становится дырой в безопасности.
