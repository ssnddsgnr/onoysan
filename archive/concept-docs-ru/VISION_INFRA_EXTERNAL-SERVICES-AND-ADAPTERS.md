# VISION_INFRA_EXTERNAL-SERVICES-AND-ADAPTERS

Этот документ описывает архитектуру интеграций Sana. Чтобы сервис оставался гибким и независимым от конкретных вендоров (будь то платежные системы, нейросети или курсы валют), мы внедряем слой **Абстрактных Адаптеров**.


--------------------------------------------------------------------------------

**Статус:** Final Infrastructure Specification

**Роль:** Изоляция внешних зависимостей и обеспечение горячей замены поставщиков услуг.

**Принцип:** «Provider Agnostic». Система не знает имен вендоров, она знает только интерфейсы.


--------------------------------------------------------------------------------

# 1. Концепция: Слой Абстракции (The Interface Layer)

В коде Sana запрещено прямое использование SDK конкретных сервисов (например, `stripe.create_payment()`). Вместо этого бизнес-логика обращается к **Типажам (Traits)** в Rust, которые определяют *что* нужно сделать, а не *как*.

## Схема взаимодействия:

**Core Logic:** Вызывает метод `PaymentProvider::charge()`.

**Adapter Layer:** Содержит конкретные реализации (StripeAdapter, PayPalAdapter).

**Factory:** На основе конфигурации (Config/Vault) подставляет нужный адаптер в рантайме.


--------------------------------------------------------------------------------

# 2. Категории изолированных сервисов

Мы выделяем четыре ключевых типа внешних API, которые должны быть полностью абстрагированы.

## А. AI & LLM (Cognitive Services)

**Адаптер:** `ModelProvider`

**Кандидаты:** Gemini (Google), Claude (Anthropic), Groq (Llama).

**Логика:** Система может одновременно использовать Gemini для архитектурного анализа и Groq для быстрой нормализации чеков, переключаясь между ними при падении одного из API.

## Б. Financial & Payments (Fiat/Billing)

**Адаптер:** `PaymentProcessor`

**Кандидаты:** Stripe, CloudPayments, Paddle.

**Логика:** Биллинг самого сервиса Sana не привязан к Stripe. Если нам нужно сменить эквайринг, мы просто пишем новый адаптер, не меняя логику подписок в БД.

## В. FX & Market Data (Currency Rates)

**Адаптер:** `ExchangeRateProvider`

**Кандидаты:** Fixer.io, CoinGecko, Binance API.

**Логика:** Для Minute-Precision FX мы можем использовать средневзвешенное значение из трех источников сразу, исключая ошибки или манипуляции курсом.

## Г. Blockchain Infrastructure (On-chain Data)

**Адаптер:** `NodeProvider`

**Кандидаты:** Infura, Alchemy, собственные ноды.

**Логика:** `sana-crypto-sync` не знает, через какой сервис он читает блокчейн. Это позволяет нам балансировать нагрузку и обходить лимиты запросов.


--------------------------------------------------------------------------------

# 3. Механика «Горячей замены» (Runtime Switching)

Выбор поставщика услуг вынесен в **Configuration Management** (K8s Secrets / HashiCorp Vault).

**Конфиг-файл (Пример):**YAML

**Multi-Provider Support:** Система может поддерживать несколько провайдеров одновременно (например, 80% трафика на Gemini, 20% на Claude для A/B тестирования или резервирования).


--------------------------------------------------------------------------------

# 4. Безопасность и Инварианты

## **Инвариант «Чистого кода»:**

В бизнес-логике (Ledger, Tax Engine, Zen) не должно встречаться названий сторонних компаний. Только функциональные интерфейсы.

## **Изоляция секретов:**

API-ключи никогда не попадают в код или логи. Они инжектируются в контейнеры как переменные окружения из защищенного хранилища.

## **Failover-автоматика:**

Если `FX_Provider_A` возвращает ошибку 5xx, Бэкенд автоматически пробует `FX_Provider_B`, сохраняя бесперебойную работу для пользователя.

## **Data Sanitization:**

Перед отправкой данных в любой внешний API (особенно в нейросети), Бэкенд обязан очистить их от PII (персональных данных) согласно политике приватности.


--------------------------------------------------------------------------------

# 5. Добавление нового сервиса (Workflow)

Чтобы добавить нового поставщика (например, новый банк), разработчик проходит три шага:

Создает новый файл `src/adapters/bank/new_bank_impl.rs`.

Реализует в нем существующий Trait `BankInformer`.

Добавляет ключ в конфигурацию Vault.

Бизнес-логика остается нетронутой.


--------------------------------------------------------------------------------

# Итог:

Sana — это модульный конструктор. Мы защищены от «vendor lock-in» (зависимости от одного поставщика). Если завтра какой-то сервис станет слишком дорогим, небезопасным или закроется, Sana продолжит работу, просто переключив «рубильник» на другого провайдера.
