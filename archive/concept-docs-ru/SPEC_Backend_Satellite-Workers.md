# 1. Философия: Орбитальная Архитектура

Для обеспечения максимальной стабильности ядра (`sana-core`), все ресурсоемкие, рискованные или длительные операции вынесены в отдельные бинарные процессы — **Спутники**.

**Изоляция ресурсов:** Генерация 100-страничного PDF-отчета не должна вызывать просадку FPS при обработке чат-сообщений.

**Изоляция паники:** Если парсер блокчейна упадет из-за некорректного ответа ноды (OOM/Panic), это затронет только один воркер. Основной API продолжит работать.

**Stateless:** Спутники не хранит состояние. Вся необходимая информация передается им в запросе или забирается из БД/Redis.


--------------------------------------------------------------------------------

# 2. Протокол коммуникации (The Umbilical Cord)

Спутники не являются независимыми микросервисами в классическом понимании (они не имеют публичного API). Они — «руки» Ядра.

**Транспорт:** **gRPC over Unix Domain Sockets (UDS)**.Внутри одного пода (Kubernetes Pod) взаимодействие происходит через файлы сокетов `/tmp/sana-worker.sock`. Это исключает TCP-оверхед и обеспечивает почти нативную скорость вызова функций.

Внутри одного пода (Kubernetes Pod) взаимодействие происходит через файлы сокетов `/tmp/sana-worker.sock`. Это исключает TCP-оверхед и обеспечивает почти нативную скорость вызова функций.

**Формат:** Строгая типизация через Protobuf.

**Управление:** `sana-core` выступает в роли **Watchdog**. Он запускает процессы спутников при старте, пингует их (Health Check) и мгновенно перезапускает при падении (Restart Policy: Always).

# 3. Реестр Спутников (Satellite Registry)

## 3.1. sana-nostradamus (Predictive Engine)

**Роль:** Тяжелая аналитика и моделирование будущего. Работает в «Медленном цикле» (Slow Loop).

**Вход:** Снапшот текущего состояния, список `recurring_patterns` (подписки) и `obligations` (долги).

**Функции:****Monte Carlo Simulation:** Прогоняет тысячи сценариев для вычисления вероятности кассового разрыва.**Goal Lag Calculation:** Рассчитывает реальную дату достижения целей с учетом инфляции и текущего Burn Rate.

**Monte Carlo Simulation:** Прогоняет тысячи сценариев для вычисления вероятности кассового разрыва.

**Goal Lag Calculation:** Рассчитывает реальную дату достижения целей с учетом инфляции и текущего Burn Rate.

**Особенность:** Запускается по расписанию (Cron) или по триггеру «Крупная покупка».

## 3.3. sana-fx-engine (Currency Gateway)

**Роль:** Обеспечение «минутной точности» (Minute-Precision FX) для мультивалютного учета.

**Архитектура:** In-Memory Cache (Redis + Local RAM).

## 3.4. sana-report-worker (Document Generator)

**Роль:** Генерация тяжелых документов для экспорта данных (Data Mobility).

**Триггер:** Сообщение в очереди RabbitMQ.

**Функции:**Собирает данные транзакций за период.Рендерит PDF с фирменной версткой (P&L, диаграммы) или собирает CSV/Excel.Загружает результат во временное S3-хранилище и возвращает ссылку Ядру.

## 3.5. sana-tax-worker (Compliance Engine)

**Роль:** Выполнение сложных налоговых расчетов, выходящих за рамки возможностей PL/pgSQL.

**Применение:** Используется для сложных юрисдикций (например, прогрессивная шкала США или специфические вычеты).

**Принцип:** Pure Function. На вход получает сумму и правила (`tax_rules`), на выход отдает сумму резерва. Не пишет в БД напрямую, возвращает результат Ядру.

## 3.6. sana-import-worker (Data Ingestion)

**Роль:** Парсинг и маппинг исторических данных при миграции пользователя.

**Вход:** CSV/XLS файлы из других систем (CoinKeeper, банковские выписки).

**Функции:**Эвристический анализ структуры файла (определение колонок даты, суммы).Маппинг категорий («Ашан» -> `food_grocery`).Группировка записей в пакеты (`import_batches`) для возможности отката.

# 4. Управление ресурсами и Лимиты

В Kubernetes для каждого спутника задаются жесткие квоты (Resource Quotas), чтобы предотвратить "шумных соседей".

| Спутник | CPU Request/Limit | RAM Request/Limit | Стратегия масштабирования |
| --- | --- | --- | --- |
| nostradamus | 0.5 / 2.0 vCPU | 512Mi / 2Gi | Horizontal (HPA) на основе CPU |
| crypto-sync | 0.1 / 0.5 vCPU | 128Mi / 512Mi | Sharding по блокчейнам |
| fx-engine | 0.1 / 0.2 vCPU | 64Mi / 256Mi | Singleton (один на регион) |
| report-worker | 0.2 / 1.0 vCPU | 256Mi / 1Gi | Queue-based (KEDA) |

# 5. Обработка ошибок (Fault Tolerance)

**Retry Policy:** Если спутник возвращает ошибку (например, таймаут внешнего API), Ядро повторяет запрос 3 раза с экспоненциальной задержкой.

**Circuit Breaker:** Если спутник падает постоянно (например, `crypto-sync` не может подключиться к ноде), Ядро временно отключает опросы этого направления и шлет уведомление в `system_broadcast`.

**Dead Letter Queue:** Задачи, которые невозможно обработать (битый CSV файл), отправляются в отдельную очередь для ручного разбора, не блокируя поток.

# Резюме

Система Спутников позволяет Sana оставаться **быстрой и отзывчивой** для пользователя, даже когда «под капотом» происходит тяжелая математика, майнинг данных блокчейна или генерация годовых отчетов. Ядро командует, Спутники исполняют.
