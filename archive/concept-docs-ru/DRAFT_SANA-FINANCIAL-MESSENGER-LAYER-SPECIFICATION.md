Этот документ представляет собой обновленную спецификацию **Sana**, фокусирующуюся на слое **финансового мессенджера**. В этой итерации мессенджер рассматривается не как отдельное приложение, а как инновационный слой взаимодействия, который дополняет основную функциональность Ledger и открывает уникальные возможности для управления коллективными финансами и бизнес-проектами.

# 1. Концепция: Финансовый протокол общения

Sana эволюционирует из классического трекера в **защищенный протокол обмена финансовыми фактами**. Мессенджер здесь — это естественная среда обитания пользователя, дополненная финансовым интеллектом.

**Приватность по умолчанию:** Обычные сообщения (текст, идеи, обсуждения) хранятся **исключительно на устройствах пользователей**. Sana не имеет доступа к истории переписки и не хранит её на своих серверах.

**Семантический Оверлей:** Sana выступает в роли «умного участника» диалога. Она активируется только при вызове через `@sana` или в отдельном системном чате с sana.

**Трансформация «Слова в Факт»:** Основная задача мессенджер-слоя — кристаллизовать хаос обсуждений в жесткую структуру `ledger_transactions`.


--------------------------------------------------------------------------------

# 2. Инварианты взаимодействия (UX & State Machine)

Для обеспечения безопасности и удобства в мессенджер-слое внедрены следующие инварианты:

**Active Session State (Индикация сессии):** При вызове ассистента интерфейс (цветовая схема) чата меняется. Это визуальный сигнал, что сейчас идет «сеанс связи» с финансовым ядром и бэкенд временно обрабатывает входящий поток данных. По завершении сессии контекст на сервере уничтожается.

**Shared Intent Consensus (Совместное согласие):** В групповых или семейных чатах создание целей или конвертов требует подтверждения участников. Sana выступает арбитром, фиксирующим «волю группы» в `access_grants`.

**Fact Mining (Кристаллизация фактов):** ИИ игнорирует эмоциональный шум переписки, так как не видит его пока явно не вызовут. Извлекает только финансовые параметры (сумма, валюта, категория, проект) для передачи в Ledger.

**Zero Trace Identity (Нулевой след):** Система оперирует только `internal_user_id`. Даже внутри чата Sana не знает реальных имен, если они не указаны в метаданных, сохраняя принцип Identity Split.

# 3. Сценарии для бизнеса и совместных бюджетов

Мессенджер-слой радикально упрощает управление сложными структурами (например, холдингами типа **ololo**).

## 3.1. Бизнес-экосистемы (Холдинги и ведомства)

**P&L в реальном времени:** Сотрудники разных ведомств (Медиа, Архитектура) фиксируют операционные расходы прямо в своих рабочих чатах. Sana мгновенно разносит их по проектам в БД.

**Межведомственные расчеты:** Переводы между отделами или оплата внутренних услуг происходят семантически: «@sana, переведи из бюджета Маркетинга в Медиа за ролик».

**Контроль ликвидности:** Руководитель холдинга видит консолидированный отчет, не покидая мессенджера, благодаря мгновенным снапшотам из `user_snapshots`.

## 3.2. Семейные и партнерские бюджеты

**Совместные конверты:** Пары могут обсуждать отпуск или крупные покупки, а Sana будет сопровождать их, создавая общие цели и отслеживая прогресс.

**Shadow Layer для приватности:** Возможность скрывать детали личных покупок в общем чате при сохранении точности общего баланса.

**Nostradamus Overlay:** Ассистент может мягко вмешаться в диалог, если планируемая трата приведет к кассовому разрыву на горизонте месяца.

# 4. Техническая архитектура слоя

**Frontend (Mobile/Web):** Локальная БД (SQLite/Realm) для хранения переписки. При вызове Sana отправляет в API только конкретное сообщение.

**Backend (Sanitary Gateway):** Проверяет авторизацию, извлекает метаданные и пробрасывает запрос Дирижёру.

**AI Layer (Conductor & Agents):** Интерпретирует запрос и возвращает в чат интерактивный виджет (например, кнопку подтверждения в `pending_layer`).

**Database (PL/pgSQL Core):** Выполняет всю математику. После записи в Ledger бэкенд возвращает в чат обновленный статус (баланс, прогресс цели).


--------------------------------------------------------------------------------

# 5. Экономика и Стратегическое преимущество

Добавление мессенджер-слоя превращает Sana в продукт с **высоким уровнем удержания (Retention)**:

**LTV и Масштаб:** При подписке 5∗∗ирасходахнатокены∗∗ **1.00**, чистая прибыль на активного пользователя составляет **~$3.40** (с учетом эквайринга).

**Позиционирование:** Sana продает не «учет», а «финансовую тишину». Вы общаетесь, а Sana гарантирует, что ваши деньги всегда под контролем и ваши секреты защищены.

# 6. Предпологаемые изменения в архитектуре

Переход к модели «финансового мессенджера» — это не только косметическое обновление интерфейса. Хотя ядро Ledger остается неизменным, архитектура требует точечных доработок на всех уровнях для обеспечения приватности и групповой логики.

Вот основные изменения:

## 1. Frontend (Самый большой объем работ)

**Локальное хранилище:** Необходимо внедрить локальную БД (например, SQLite или Realm) на устройствах пользователей, так как сервер больше не хранит историю сообщений.

**State Machine интерфейса:** Реализация механизма смены цветовых схем и состояний при активации сессии с `@sana`.

## 2. Backend (Слой управления сессиями)

**Sanitary Gateway:** Доработка шлюза для обработки входящих интентов из чатов без сохранения их в базу данных.

**Session Manager:** Логика управления «активным состоянием» сессии, которая открывает временный контекст для ИИ-слоя и уничтожает его сразу после выполнения транзакции.

## 3. Database (Слой метаданных)

**Групповые сущности:** В схему `ledger` или `system` нужно добавить таблицы для управления «комнатами» или группами (ID группы, список `internal_user_id` участников), чтобы Sana понимала контекст совместного доступа.

**Access Grants:** Расширение логики прав доступа для мгновенного включения участников чата в `Shared Domain` создаваемых целей или конвертов.

### Дополнение: Слой социальной идентификации (User Identity)

Для обеспечения быстрой навигации и формирования чувства причастности к сервису, профиль пользователя Sana расширяется набором узнаваемых атрибутов. Это позволяет пользователям находить друг друга и связывать аккаунты для совместного ведения бюджетов без необходимости обмена сложными UUID.

### Состав профиля (Data Points):

**Имя и Фамилия:** Для официальной отчетности внутри команд и ведомств.

**Nickname (Уникальный):** Главный инструмент поиска и самоидентификации. Служит для быстрого упоминания в чатах (`@nickname`) и связки аккаунтов.

**Email:** Для системных уведомлений и восстановления доступа.

**Telegram ID (Automated):** Привязывается автоматически при первом входе. Позволяет системе бесшовно узнавать пользователя в мессенджере и сопоставлять его сообщения с `internal_user_id`.

Зачем это нужно: Никнейм упрощает «командную магию». Вместо того чтобы просить у коллеги длинный ID, тимлид просто находит его по нику и добавляет в финансовый поток проекта.

## 4. ИИ-слой (Дирижёр)

**Фильтрация шума:** Промпты Дирижёра должны быть дополнены инструкциями по игнорированию не-финансового контента («эмоционального шума») внутри чат-сессий.

# Итог:

Мессенджер-слой Sana — это не дополнение к мессенджеру, а **способ сделать финансы частью коммуникации**. Для фрилансеров, семей и таких структур, как ololo, это означает переход от бюрократического учета к мгновенному управлению на основе данных.
