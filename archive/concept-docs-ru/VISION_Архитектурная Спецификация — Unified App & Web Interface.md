# VISION_Архитектурная Спецификация — Unified App & Web Interface

Этот документ описывает визуальную и интерфейсную стратегию Sana. Мы создаем **Bimodal Interface** (бимодальный интерфейс), который сочетает в себе гибкость естественного языка и строгость визуальных данных. Это «центр управления финансовым суверенитетом» на вашем смартфоне и в браузере.


--------------------------------------------------------------------------------

Статус: Final UI/UX Specification

Концепция: «Chat-First, Visual-Driven»

Платформы: iOS, Android, Web (PWA/SPA)


--------------------------------------------------------------------------------

# 1. Бимодальная архитектура: Два окна — одна правда

Интерфейс Sana разделен на две основные рабочие области, между которыми пользователь переключается мгновенным свайпом или кликом.

## А. Окно 1: Cognitive Chat (Когнитивный слой)

Это «Мозг» системы. Здесь происходит общение с ИИ-агентами.

**Чат-интерфейс:** Основная лента активного диалога.

**Менеджер чатов:** Боковая панель (или вкладка) со списком чатов.**Папки:** Группировка диалогов по Проектам, Целям или Тегам (согласно логике TTL и связей в БД).**Поиск:** Глобальный поиск по смыслам и заметкам во всей истории диалогов.

**Папки:** Группировка диалогов по Проектам, Целям или Тегам (согласно логике TTL и связей в БД).

**Поиск:** Глобальный поиск по смыслам и заметкам во всей истории диалогов.

## Б. Окно 2: Visual Dashboard (Слой Реальности)

Это «Тело» системы. Визуализация состояния Ledger в реальном времени.

**Wallets (Физика):** Вкладка с актуальными балансами всех счетов (карта, нал, крипта).

**Envelopes (Логика):** Вкладка с распределением средств по конвертам трат.

**Goals (Будущее):** Прогресс-бары целей с цветовой индикацией «здоровья» (на основе Goal Lag из БД).

**Charts:** Интерактивные графики P&L (прибыли и убытки), динамика чистой стоимости (Net Worth) и прогнозы кассовых разрывов от Nostradamus.

# 2. Навигация и управление (The Burger & Global UI)

### Burger Menu (Административный хаб)

Вызываемое меню для глубоких настроек и управления аккаунтом:

**Account:** Профиль, верификация Email/Telegram, управление сессиями.

**Billing:** Подписка, история платежей за сервис.


--------------------------------------------------------------------------------

# 3. Модули, которые мы добавили (Critical UI Components)

Для полной функциональности мы интегрируем в интерфейс следующие элементы:

## А. Pending Inbox (Центр Внимания)

Специальный индикатор или мини-окно, где отображаются «зависшие» события из **Pending Layer**.

Красная точка с числом нераспознанных транзакций или запросов от команды.

При клике открывается список карточек, требующих «Минимального волевого акта» (подтвердить/отклонить/уточнить).

## Б. Nostradamus Outbox (Почтовый ящик гипотез)

Раздел в Дашборде, где хранятся сгенерированные ИИ-прогнозы и предложения по оптимизации.

*«Я рассчитала новый план для цели 'Квартира'. Посмотреть?»*

## В. Reality Sync Trigger (Кнопка Сверки)

Быстрая кнопка «Сверить баланс» на вкладке кошельков. Вызывает упрощенный диалог ввода реального остатка для моментальной корректировки Ledger.


--------------------------------------------------------------------------------

# 4. Технологический стек фронтенда

**Framework:** Flutter или React Native (для единого кода iOS/Android) + React/Next.js для Web.

**State Management:** Синхронизация через gRPC-web или WebSocket для мгновенного обновления балансов на дашборде при совершении транзакции в чате.

**Security:** Биометрия (FaceID/TouchID) для входа в приложение, защита от скриншотов в конфиденциальных разделах.


--------------------------------------------------------------------------------

# 5. UX-инварианты

**Инвариант Синхронности:** Любое изменение в чате (например, «запиши 100 на еду») должно мгновенно отобразиться на Дашборде без перезагрузки страницы.

**Инвариант Доступности:** Самые важные цифры (Net Worth и ближайший риск кассового разрыва) всегда видны в верхней части экрана.

**Инвариант Легкости:** Интерфейс не должен быть перегружен. Так же сервси определяет где человек в последний раз взаимодействовал с сервисом и пишет туда, если человек писал в бота, а у сервиса есть сообщения на отправку то, он напишет ему в бота, а не в приложение, тоже самое — наоборот, web-интерфейс в этой механике игнорируется.
