# VISION_Архитектурная Спецификация — Ядро Архитектуры Backend. Детерминированный Оркестратор

Технологический стек: Rust (Core & Satellites), PostgreSQL (Logic & Storage), gRPC (Internal Communication).


--------------------------------------------------------------------------------

# 1. Философия Ядра (The Core Philosophy)

Backend Sana не является монолитным приложением, которое «делает всё». Это **Экосистема Детерминизма**, построенная по принципу «Ядро и Спутники» (Core & Satellites).

## Принцип Цензора:

Backend не доверяет ИИ. Любой интент от LLM рассматривается как *потенциально ошибочный*, пока не пройдет валидацию.

## Принцип Изоляции:

Отказ одного модуля (например, парсера крипты) никогда не должен останавливать работу основного Леджера.

## Принцип «Logic in Data»:

Вся финансовая математика и транзакционная целостность находятся внутри PostgreSQL (PL/pgSQL), а не в коде приложения.


--------------------------------------------------------------------------------

# 2. Топология Системы: Архитектура «Созвездие»

Система состоит из одного управляющего процесса (Master) и набора автономных бинарных микросервисов (Satellites).

## 2.1. Master Process: `sana-core` (Rust)

Это центральный оркестратор. Он «легкий», быстрый и отказоустойчивый.

**API Gateway:** Принимает соединения (gRPC/REST) от Telegram-бота, приложения, web и Frontend.

**Intent Validator:** Проверяет схемы данных (JSON Schema Validation).

**Process Manager:** Запускает, мониторит и перезапускает спутники (`Health Checks`, `Watchdog`).

**DB Connector:** Единственная точка записи в базу данных (Connection Pool).

## 2.2. Satellite Binaries (Спутники)

Изолированные процессы, выполняющие специализированные задачи. Общаются с ядром через **gRPC**.

| Бинарник | Роль | Особенности |
| --- | --- | --- |
| sana-nostradamus | AI Analytics Engine. Работает с Gemini 1.5 Pro. Выполняет тяжелые вычисления, строит прогнозы, анализирует паттерны трат. | Имеет ограничение по CPU/RAM, чтобы не замедлять ядро. Работает в Slow Loop. |
| sana-crypto-sync | Blockchain Parser. Асинхронно опрашивает внешние API (Etherscan, BTC Nodes, Exchange APIs). | Stateless. При падении перезапускается sana-core мгновенно. |
| sana-fx-engine | Currency Gateway. Кэширует курсы фиатных валют. | Обновляется раз в N минут. Предоставляет данные из RAM (Zero Latency). |
| sana-tax-worker | Compliance Engine. Рассчитывает сложные налоговые сценарии (например, прогрессивные шкалы) перед записью. | Pure functions (без побочных эффектов). |

# 4. Слой данных: Logic in Database (PostgreSQL)

Мы переносим бизнес-логику в БД для гарантии атомарности. Backend лишь дергает «ручки» этих функций.

## Ключевые PL/pgSQL функции (API базы данных):

**rpc_create_transaction(jsonb)**: Универсальная функция входа. Разбирает JSON внутри базы.

**rpc_sync_reality(wallet_id, real_balance)**: Функция для Reality Sync. Создает корректирующую транзакцию (Adjustment), чтобы подогнать систему под факт.

**rpc_distribute_income(amount)**: Функция «Водопад». Автоматически раскидывает входящий доход по фондам и налогам согласно правилам пользователя.

## Инвариантные Триггеры (The Watchdogs):

**trg_check_ledger_balance**: После каждой вставки проверяет уравнение `Assets = Liabilities + Equity`. Если не сходится — `RAISE EXCEPTION`.

**trg_prevent_history_rewrite**: Блокирует любые `UPDATE` или `DELETE` в таблице `transactions`.

# 6. Отказоустойчивость (Resilience)

**Изоляция паники:** Если `sana-nostradamus` упадет из-за ошибки памяти (OOM), `sana-core` просто перезапустит процесс. Пользователь этого не заметит (транзакции продолжат ходить).

**Transaction Rollback:** Любая ошибка на этапе PL/pgSQL вызывает полный откат транзакции. Деньги не могут «зависнуть» или «исчезнуть».

**Dead Letter Queue:** Если AI присылает невалидные интенты, они логируются в отдельную таблицу для анализа (почему ИИ ошибся?), но не влияют на балансы.
