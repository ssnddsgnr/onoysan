Этот документ является итоговым техническим дополнением к **VISION** и **DRAFT** спецификациям системы Sana. Он объединяет структуру данных, логику агрегации и новые функциональные блоки (Shared Sovereignty, Nostradamus, Data Mobility) в единый проектный манифест для последующей разработки и анализа в NotebookLM.

**Статус:** Working Draft

**Цель:** Описание полной экосистемы таблиц и логических связей для реализации финансовой трезвости, ИИ-управления и совместного доступа.

# 1. Слой Идентификации и Доступа (Security & Sovereignty)

Этот слой изолирует личность от финансов и управляет правами доступа в рамках совместного использования.

## 1.1. Аутентификация и Метаданные

**auth_identities**: Связывает внешние ID (Telegram, Email) с анонимным `internal_user_id`. Единственная точка входа в систему.

**users_metadata**: Зашифрованные данные пользователя (имя для ИИ, базовая валюта, таймзона — системная по Гринвичу и локальная для UX).

## 1.2. Shared Sovereignty (Совместный доступ)

Для реализации неограниченного шеринга бюджета и управления ролями вводится таблица управления доступом:

**access_grants**: Реализует **RBAC** (Role-Based Access Control).**Resource Types**: `wallet`, `project`, `envelope`.**Roles**: `viewer`, `editor`, `requester`, `manager`.**Expiration**: Поддержка временного доступа через `expires_at`.

**Resource Types**: `wallet`, `project`, `envelope`.

**Roles**: `viewer`, `editor`, `requester`, `manager`.

**Expiration**: Поддержка временного доступа через `expires_at`.

# 2. Слой Финансовых Сущностей (The Mirror Layers)

## 2.1. Wallets (Физический уровень)

Иерархическая модель для устранения когнитивного шума:

**Parent Wallet**: Группировка по устройству/бирже (напр., Ledger, Binance).

**Child Mirror Wallet**: Конкретный актив внутри родителя (BTC, ETH, USD).

**System Account**: Виртуальный «General Ledger», используемый по умолчанию, если счета не добавлены.

## 2.2. Envelopes (Логический уровень)

Обязательные поля: `priority`, `target_amount`.

Дополнительное поле: **target_date** для расчета **Goal Lag** (отставания от графика накопления).

Типы: `obligation`, `reserve`, `saving`, `free_spend`.

## 2.3. Obligations & Recurring Patterns (Будущие потоки)

**obligations**: Учет конкретных долгов (Payable/Receivable) с контрагентами и дедлайнами.

**recurring_patterns**: База для модуля **Nostradamus**. Хранит регулярные подписки (Netflix, Аренда) с частотой списания и датой следующего платежа.

## 2.4. Обязательные и Рекомендованные конверты:

**Обязательные (Mandatory):** Налоги, аренда, кредиты. Если баланс в таких конвертах ниже требуемого (на основе `tax_rules` или `recurring_patterns`), система идентифицирует это как критическую зону.

**Рекомендованные (Recommended):** Финансовая подушка, амортизация авто.

**Проактивная логика:** Если на физических счетах пользователя недостаточно средств для покрытия этих конвертов, ИИ не просто констатирует факт, а инициирует диалог: *«Для полной безопасности нам не хватает $400 в резервах. Хочешь создать цель 'Накопить на налоги' с ежемесячным планом $100?»*.

## 2.3. Гибкость и модификация сумм:

Все параметры конвертов (`target_amount`, `priority`, `target_date`) являются **изменяемыми** в любой момент времени.

Изменение лимита в одном конверте автоматически запускает пересчет показателя **Safe-to-Spend** в реальном времени.

## 2.5. Разграничение «Целей» и «Накоплений»:

**Фиксированные Цели (Goals):** Имеют жесткую сумму (`target_amount`) и, как правило, дедлайн (`target_date`). При достижении 100% система предлагает подтвердить целевое списание.

**Бессрочные Накопления (Savings):** Конверты для аккумулирования излишков без конкретной покупки.

**Логика расширения:** Если сумма в «Накоплениях» достигает установленного лимита, но пользователь не совершает трат из этого конверта, Sana анализирует его финансовое поведение. ИИ предложит: *«Ты достиг цели в $5,000 в накоплениях, и твои доходы стабильны. Хочешь увеличить планку до $7,000 или распределить излишек в инвестиционные проекты?»*.

# 3. Ядро Реестра и Валютные Снапшоты (The Core)

## 3.1. Ledger Transactions (Immutable Stream)

Центральный реестр всех событий.

**Инвариант**: ∑Wallets≡∑Envelopes.

**Связи**: `wallet_id`, `envelope_id`, `project_id`, `asset_id`, `message_id`.

**Классификация**: `merchant_name`, `category_slug`, `subcategory_slug`, `user_note` (авто-извлечение ИИ).

**Теги**: Массив тегов, включая **hidden** для активации Shadow Layer (скрытие из общих отчетов).

## 3.2. FX Rates & Rollup Policy

Для обеспечения «Minute-Precision FX» используется таблица курсов с механизмом затухания:

**fx_rates_history**: Хранит курсы в масштабах `1m`, `1h`, `1d`.

**Rollup Policy**: Минутные записи старше 24 часов схлопываются в часовые, часовые старше 30 дней — в дневные.


--------------------------------------------------------------------------------

# 4. Слой Бизнес-Логики и Проектов

## 4.1. Project-Based P&L

**projects**: Контейнеры для бизнес-целей. Включают поле **archived_at** для управления жизненным циклом связанных чатов.

**tax_rules**: Правила авто-резервирования (Режимы A, B, V).

**project_balances**: Агрегированные данные для расчета **Чистой прибыли** проекта в реальном времени (Доход - Расходы - Налоги - Обязательства).


--------------------------------------------------------------------------------

# 5. Когнитивный Слой (AI & UX)

## 5.1. Chat & Pending Layer

**chat_sessions** & **chat_messages**: Хранят контекст и мультимодальную историю (фото чеков, аудио).

**pending_layer**: Буфер для транзакций, требующих «Минимального волевой акта» (подтверждения пользователем).


--------------------------------------------------------------------------------

# 6. Аналитика и Техническое Состояние

## 6.1. Snapshots Engine

**user_snapshots**: Оперативный снапшот (Net Worth, Safe-to-Spend, Tax Reserve). Обновляется триггером `PL/pgSQL` при каждой транзакции.

**balance_snapshots_history**: История балансов на конец дня (EOD) для построения графиков динамики капитала.

## 6.2. Вспомогательные таблицы

**blockchain_cursors**: Хранит последний отсканированный блок для каждой крипто-сети (`sana-crypto-sync`).

**import_batches**: Группировка импортированных данных из внешних систем (CSV/Excel) для возможности массового отката.

**system_audit_logs**: Логирование изменений настроек, прав доступа и действий администраторов.


--------------------------------------------------------------------------------

# Резюме архитектуры:

Система Sana строится на принципе **атомарности**: любая запись в Ledger одновременно обновляет `user_snapshots`, проверяет `tax_rules` и учитывает `recurring_patterns`. Это создает фундамент для ИИ, который не просто «считает цифры», а понимает финансовый контекст и обеспечивает пользователю истинную «финансовую трезвость».
