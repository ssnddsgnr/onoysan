# 1. Фундамент: Оркестрация и Вычисления (Compute Layer)

Инфраструктура Sana строится на принципах **Иммутабельности**. Мы не «чиним» серверы, мы заменяем их новыми образами. В основе лежит Kubernetes, обеспечивающий изоляцию процессов и управление ресурсами.

## 1.1. Kubernetes (K8s) Runtime

**Distroless Images:** В продакшене используются Docker-образы без оболочки (shell) и лишних системных библиотек. Это минимизирует поверхность атаки — злоумышленнику буквально нечего запускать внутри контейнера, даже если он туда попадет.

**Resource Quotas & Limits:** Для каждого пода заданы жесткие лимиты CPU и RAM. Процессы-спутники (например, `sana-report-worker`) изолированы так, чтобы их «прожорливость» при генерации отчетов никогда не влияла на скорость работы основного Ядра (`sana-core`).

## 1.2. Sana Core (Rust Backend)

Ядро системы работает в Native-режиме (без виртуальных машин языков типа JVM). Rust гарантирует отсутствие ошибок памяти (Memory Safety), что критично для высоконагруженных финансовых расчетов и предотвращает целый класс уязвимостей (buffer overflow).

# 2. Сетевая топология: «Крепость в три кольца»

Мы реализуем физическое разделение сети на изолированные сегменты (VLANs/Subnets) с жесткими правилами маршрутизации. Доступ «снаружи внутрь» запрещен по умолчанию.

## Зона 1: Public Zone (The Shield / Щит)

**Компоненты:** Cloudflare WAF, Application Load Balancer (ALB).

**Доступ:** Единственная точка соприкосновения с интернетом.

**Функция:** Принимает только зашифрованный HTTPS-трафик (Webhooks от Telegram, запросы от мобильного приложения), фильтрует DDoS и ботов, терминирует SSL.

## Зона 2: Private Backend Zone (The Brain / Мозг)

**Компоненты:** Поды `sana-core`, `sana-conductor` (AI Logic), Спутники (`nostradamus`, `crypto-sync`).

**Доступ:** Прямой доступ из интернета **закрыт**. Входящий трафик разрешен только от ALB из Public Zone.

**Связь:** Компоненты общаются между собой через gRPC (mTLS), обеспечивая защищенный канал внутри кластера.

## Зона 3: Private Data Zone (The Vault / Сейф)

**Компоненты:** PostgreSQL, Redis, RabbitMQ.

**Доступ:** Эта зона полностью отрезана от публичного интернета (No Internet Access). Доступ к портам БД разрешен **только** подам из Private Backend Zone по белому списку IP.

**Изоляция:** Даже если хакер взломает ALB, он не сможет «достучаться» до базы данных напрямую, так как сетевые маршруты отсутствуют.

# 3. Фабрика Данных: Политики Хранения (Data Fabric)

Sana придерживается строгой иерархии хранения данных, разделяя их по ценности и времени жизни.

## 3.1. PostgreSQL (Single Source of Truth)

**Роль:** Вечное хранение. Единственный источник истины.

**Принцип доступа:** **Exclusive Owner**. Ядро системы (`sana-core`) является монопольным владельцем пула соединений на запись. Прямой доступ к таблицам для других сервисов физически закрыт.

**Безопасность:** Row-Level Security (RLS) активировано принудительно для всех соединений, гарантируя изоляцию данных пользователей на уровне движка БД.

## 3.2. Redis (Ephemeral Buffer)

**Роль:** Оперативная память и кэш.

**Данные:** «Горячие» курсы валют (Minute-Precision FX), сессии пользователей, распределенные блокировки.

**Инвариант Чистоты:** **Строжайше запрещено** хранить в Redis данные Ledger или транзакций. Redis считается ненадежным хранилищем (Volatile Storage), потеря которого не должна приводить к финансовым расхождениям.

## 3.3. Object Storage / S3 (Transit Media)

**Роль:** Временный буфер для неструктурированных данных (фото чеков, аудио).

**Lifecycle Policy:***Входящие:* Фото и аудио удаляются **немедленно** после успешного извлечения интентов (OCR/Transcription).*Исходящие:* Сгенерированные PDF-отчеты хранятся с TTL 24 часа, после чего физически уничтожаются.

*Входящие:* Фото и аудио удаляются **немедленно** после успешного извлечения интентов (OCR/Transcription).

*Исходящие:* Сгенерированные PDF-отчеты хранятся с TTL 24 часа, после чего физически уничтожаются.

**Приватность:** Мы не храним архивы личных фото пользователей.

# 4. Нервная система: Асинхронная коммуникация

Для обеспечения отказоустойчивости и архитектуры «Созвездие» используется шина сообщений.

**RabbitMQ / NATS:** Выступает магистралью для событий, развязывая (decoupling) прием данных и их обработку.*Пример:* `sana-crypto-sync` находит новую транзакцию в блокчейне и кладет событие в очередь. Backend забирает его, когда готов, сглаживая пиковые нагрузки.

*Пример:* `sana-crypto-sync` находит новую транзакцию в блокчейне и кладет событие в очередь. Backend забирает его, когда готов, сглаживая пиковые нагрузки.

**Dead Letter Queue (DLQ):** Изолятор для событий, вызвавших ошибку (например, битый JSON от банка). Это предотвращает бесконечные циклы перезапуска задач и позволяет инженерам анализировать сбои без остановки системы.

# 5. Безопасность и Zero-Trust Инфраструктура

## 5.1. Secret Management (Управление секретами)

Sana следует принципу **«Secretless Code»**.

В исходном коде и Docker-образах отсутствуют API-ключи, пароли от БД или ключи шифрования.

**Механизм:** Секреты инжектируются в процесс `sana-core` только в момент запуска (Runtime Injection) из **HashiCorp Vault** или K8s Secrets через переменные окружения или in-memory тома.

## 5.2. Admin Access (Reactive Admin Protocol)

Админ-панель (Appsmith) находится строго внутри VPN.

Доступ к данным осуществляется не через прямой SQL, а через вызов безопасных PL/pgSQL процедур, что исключает возможность случайного удаления данных администратором.

# 6. Observability (PLG Stack)

Мы строим систему мониторинга «здоровья», чтобы видеть проблемы до того, как их заметит пользователь.

**Prometheus:** Сбор метрик (RPS, задержки, потребление памяти, отставание сканера блокчейна).

**Loki:** Централизованный сбор логов.**PII Masking:** Входящий поток логов проходит через фильтр, который автоматически маскирует персональные данные (email, телефоны, адреса кошельков), обеспечивая приватность даже на уровне логов отладки.

# Резюме архитектора

Инфраструктура Sana спроектирована как **неубиваемая система**.

**Топология** из трех зон защищает ядро данных от атак извне.

**Kubernetes** и **Rust** обеспечивают надежность исполнения и изоляцию сбоев.

**Политики хранения** гарантируют, что финансовая истина вечна (PG), а чувствительный мусор (фото, кэш) — эфемерен.

Это создает среду, где **Детерминизм** обеспечивается не только кодом, но и самой физикой инфраструктуры.
