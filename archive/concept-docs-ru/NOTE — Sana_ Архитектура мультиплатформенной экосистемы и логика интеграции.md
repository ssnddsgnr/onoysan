Пересборка архитектуры Sana с учетом новых точек контакта, логики маршрутизации и стратегии оплаты превращает сервис в гибкую мультиплатформенную экосистему. Теперь Sana — это единый финансовый интеллект, доступный там, где удобно пользователю, с приоритетом на суверенное владение данными.

### 1. Расширенная карта точек контакта (Bimodal UX)

Система реализует принцип **«Один мозг — три окна»**. Функционал Web и App идентичен: оба предоставляют полный доступ к когнитивному чату и визуальному дашборду.

- **Мобильное приложение (iOS/Android):** Основной хаб. Хранит полную историю переписки локально (SQLite) и синхронизирует её с сервером.

- **Web-интерфейс:** Полноценное зеркало приложения для работы с компьютера. Использует те же механизмы синхронизации и визуализации.

- **Telegram-бот:** Легкая точка входа. Работает в режиме **эфемероности** — история сообщений внутри самого бота не хранится, но все взаимодействия мгновенно фиксируются в глобальном Ledger и отображаются в приложении/Web.

### 2. Интеллектуальная маршрутизация (Routing Logic)

Для минимизации когнитивного шума внедряется **Инвариант Легкости**, управляющий каналами связи:

- **Приоритет «App-First»:** По умолчанию Sana инициирует общение через push-уведомления мобильного приложения.

- **Триггер переключения:** Сервис определяет, где пользователь взаимодействовал с ним в последний раз. Если последнее сообщение пришло из Telegram-бота, ответ системы уйдет в бота, а не в приложение.

- **Синхронизация «Bot-to-App»:** Хотя в Telegram история отсутствует, каждое сообщение пользователя в боте получает message_id, по которому транзакции связываются в Ledger. При открытии приложения пользователь видит эти сообщения в общей ленте благодаря серверной синхронизации chat_messages.

### 3. Экономика и Биллинг: Стратегия обхода комиссий

Для сохранения маржинальности и избежания сборов сторов (15-30%) вся финансовая часть сервиса выносится за пределы мобильных платформ.

- **Слой оплаты (Payment Layer):** В External Adapters Factory реализуется типаж PaymentProvider, ориентированный на **Stripe**.

- **Точки оплаты:** Оформление подписки происходит только через Web-интерфейс или платежный шлюз Telegram. Это позволяет снизить транзакционные издержки до 2-3%.

- **Управление в БД:** Таблица billing (в схеме auth или system) отслеживает статус подписки, историю платежей и привязанные методы оплаты, обеспечивая доступ ко всем точкам контакта после верификации.

### 4. Технические изменения в структуре данных

Чтобы поддержать эту логику, вносятся точечные изменения в схему идентификации:

1. **Таблица auth_identities:** Поле last_seen_at дополняется метаданными о канале (app, web, bot), чтобы Дирижёр знал, куда отправить финальный ответ Zen.

2. **Таблица chat_messages:** Поле content_type теперь может помечать system_event (например, уведомление об оплате через Stripe в Web), которые будут красиво отрисованы в ленте приложения.

3. **Identity Split:** Принцип разделения сохраняется — платежные данные в Stripe связываются только с анонимным internal_user_id, не раскрывая финансовое ядро Ledger внешнему провайдеру.

### Итог:

Sana становится **вездесущим ассистентом**. Пользователь может начать обсуждение кредита в Web-интерфейсе за рабочим столом, подтвердить транзакцию через Telegram на бегу, а вечером просмотреть итоговый график P&L в мобильном приложении.
