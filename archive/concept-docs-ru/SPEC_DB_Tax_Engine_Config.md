**Налоги живут на уровне кошелька**. Это упрощает UX (настроил один раз для счета ИП и забыл), но оставляет архитектурную возможность для исключений (специфические проекты) через механизм переопределения.

**Концепция:** Wallet-Centric Compliance (Налогообложение по месту хранения) **Роль:** Фоновый процесс, гарантирующий налоговую чистоту средств. **Принцип:** «Настроил счет — забыл про налоги». Система применяет правила счета ко всем входящим транзакциям по умолчанию.

# 1. Архитектура: Иерархия Правил

Tax Engine использует двухуровневую систему поиска правил для каждой доходной транзакции (Income). Это предотвращает необходимость настраивать налоги для каждого нового проекта, но сохраняет гибкость для сложных контрактов.

## 1.1. Логика Приоритетов (The Hierarchy)

При поступлении дохода система ищет применимое правило в следующем порядке:

**Уровень 1: Исключение (Project Override).** Сначала проверяется, есть ли специфичное правило для `project_id`. Это используется для редких случаев (экспортные контракты, гранты без налогов, партнерские сделки с особыми условиями).

**Уровень 2: Стандарт (Wallet Default).** Если проектного правила нет, применяется правило, привязанное к `wallet_id`. **Это основной сценарий для 95% пользователей.**

**Нет правила:** Если ни для проекта, ни для кошелька правил нет — налог не начисляется, в основном это обычные кошельки пользователя, даже если он получил деньга за работу на свой простой счёт, мы не станем обязывать его платить налоги мы привязываем налоги только к юридическим счетам, которые "видит" налоговая.

## 1.2. Таблица конфигурации: `tax_rules`

| Поле | Тип | Описание и Логика |
| --- | --- | --- |
| id | UUID | PK. Уникальный ID правила. |
| internal_user_id | UUID | FK. Владелец правила. |
| wallet_id | UUID | (Optional) Базовое правило. Ссылка на физический счет (например, «Счет ИП в Kaspi»). Если правило активно, любой доход на этот счет облагается налогом. |
| project_id | UUID | (Optional) Правило-Исключение. Ссылка на проект. Если заполнено, имеет приоритет над правилом кошелька. |
| tax_mode | VARCHAR(1) | Режим расчета: 'A' (Оборот), 'B' (Прибыль), 'V' (НДС/VAT). |
| tax_rate | NUMERIC | Ставка налога (например, 0.06 для 6%). |
| tax_envelope_id | UUID | Ссылка на конверт «Налоговый резерв», куда будут заморожены средства (Locked Funds). |
| deductible_categories | JSONB | Список слагов категорий (['software', 'rent']), которые уменьшают налоговую базу (для Режима B). |
| is_active | BOOLEAN | Флаг активности правила. |

**UX Best Practice:** В интерфейсе пользователь при создании кошелька типа `business` сразу получает предложение настроить налог. Для проектов эта настройка спрятана в раздел «Advanced».

# 2. Режимы налогообложения (Algorithms)

Система поддерживает три алгоритма, покрывающих большинство юрисдикций.

### 2.1. Режим A: Налог с оборота (Revenue-Based)

Идеально для: ИП на упрощенке (6%), Самозанятых.

**Триггер:** Транзакция `income` на целевой кошелек.

**Формула:** Reserve=Amountincome​×Rate

**Сценарий:**На счет «ИП» пришло 100 000. Правило кошелька: 6%.Система создает техническую транзакцию: Перевод 6 000 в конверт «Налоги».Пользователь видит в «Свободных деньгах»: 94 000.

На счет «ИП» пришло 100 000. Правило кошелька: 6%.

Система создает техническую транзакцию: Перевод 6 000 в конверт «Налоги».

Пользователь видит в «Свободных деньгах»: 94 000.

## 2.2. Режим B: Налог с прибыли (Net Income)

Идеально для: Торговли, Производства (Доходы минус Расходы).

**Механика:** Работает накопительным итогом в рамках **налогового периода** (обычно год/квартал).

**Триггер 1 (Доход):** Резервирует налог с полной суммы (защитная стратегия), как в Режиме А.

**Триггер 2 (Расход):** Если расход попадает в `deductible_categories` (например, «Закупка товара»):Уменьшается налогооблагаемая база.Система **возвращает** излишне зарезервированный налог из конверта «Налоги» в конверт «Свободные деньги».

Уменьшается налогооблагаемая база.

Система **возвращает** излишне зарезервированный налог из конверта «Налоги» в конверт «Свободные деньги».

**Формула возврата:** Return=ExpenseAmount×Rate

## 2.3. Режим V: НДС / Косвенные налоги (VAT)

Идеально для: Плательщиков НДС.

**Логика:** Выделение налога **сверх** или **внутри** суммы.

**Сценарий:** Пришел платеж 1200 (в т.ч. НДС 20%).Wallet: +1200.Envelope Income: +1000 (Выручка).Envelope VAT: +200 (Обязательство).

Wallet: +1200.

Envelope Income: +1000 (Выручка).

Envelope VAT: +200 (Обязательство).

# 3. Исполнение в Базе Данных (PL/pgSQL Implementation)

Вся логика инкапсулирована в функции `tax.fn_calculate_tax_reserve()`. Это гарантирует атомарность: доход и налог записываются в одной транзакции БД.

## 3.1. Алгоритм Триггера (`AFTER INSERT` on `ledger_transactions`)

```
-- Псевдокод логики выбора правила
DECLARE
  v_rule RECORD;
BEGIN
  -- 1. Сначала ищем специфичное правило для ПРОЕКТА (Exception)
  SELECT * INTO v_rule FROM tax_rules
  WHERE project_id = NEW.project_id AND is_active = TRUE;

  -- 2. Если не нашли, ищем правило для КОШЕЛЬКА (Default)
  IF v_rule IS NULL THEN
    SELECT * INTO v_rule FROM tax_rules
    WHERE wallet_id = NEW.wallet_id AND is_active = TRUE;
  END IF;

  -- 3. Если правила нет вообще -> Выход
  IF v_rule IS NULL THEN
    RETURN NEW;
  END IF;

  -- 4. Выполняем расчет резерва по найденному правилу
  PERFORM tax.internal_execute_reservation(NEW.id, v_rule);

  RETURN NEW;
END;

```

# 4. Инварианты и Безопасность

**Приоритет государства:** Налоговый триггер срабатывает **до** распределения по целям и фондам.

**Locked State (Заморозка):** Средства в конверте `tax_envelope_id` исключаются из расчета `safe_to_spend`. Система запрещает тратить их на что-либо, кроме категории `tax_payment`.

**Аудит:** Каждая налоговая запись имеет ссылку `parent_tx_id` на исходный доход. Это позволяет построить отчет: «Покажи, из каких поступлений сформировался этот налоговый долг».

# 5. P&L Проектов (Project Profitability)

Даже если налог настроен глобально на Кошельке (например, 6% на всё ИП), система корректно атрибутирует налог к Проектам.

Если пришло 1000 по Проекту А на Кошелек ИП -> Списалось 60 налога.

В таблице `project_balances` для Проекта А:`total_income`: 1000`tax_reserved`: 60`net_profit`: 940

`total_income`: 1000

`tax_reserved`: 60

`net_profit`: 940

**Итог:** Мы видим чистую прибыль проекта, даже используя «общекотловое» правило налога для кошелька.
