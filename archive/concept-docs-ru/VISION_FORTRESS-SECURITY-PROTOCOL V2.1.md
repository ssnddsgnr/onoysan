Этот документ определяет философию и технические протоколы безопасности Sana. Мы строим систему на фундаменте **недоверия к среде** и **абсолютной защиты субъекта**, где безопасность данных важнее удобства разработки.


--------------------------------------------------------------------------------

**Статус:** Final Security Specification

**Роль:** Защита финансовой и личностной целостности пользователя.

**Принцип:** «Privacy by Design, Security by Default».


--------------------------------------------------------------------------------

# 1. Базовые принципы и «Нулевое доверие» (Zero Trust)

В Sana ни один компонент системы не считается безопасным по умолчанию.

**Verify Everything:** Каждый запрос между Backend, БД и AI-агентами должен быть аутентифицирован.

**Least Privilege:** Любой воркер или агент имеет доступ только к тем данным, которые необходимы для выполнения текущей задачи.

**Backend as a Sanitary Gateway:** Все сообщения от пользователей (из Telegram, Web или App) сначала попадают на **Backend** для проверки авторизации и извлечения системных метаданных. Только после валидации сессии очищенный запрос перенаправляется **Дирижёру**.

**Изоляция:** Взлом одного компонента (например, Telegram-бота) не дает доступа к Ledger, так как они разделены сетевыми и логическими барьерами.


--------------------------------------------------------------------------------

# 2. Разрыв идентичности (Identity Separation)

Мы внедряем **Identity Split**, чтобы исключить связь между реальным человеком и его деньгами в случае утечки.

**Layer 1 (Public Auth):** Хранит `telegram_id` / `email` и сопоставляет их с анонимным `UUID`.

**Layer 2 (Private Core):** Хранит финансовые данные, привязанные только к анонимному `UUID` (internal_user_id).

**Результат:** База данных Ledger не знает, как вас зовут и какой у вас Telegram. Она знает только анонимный идентификатор.


--------------------------------------------------------------------------------

# 3. Защита на уровне данных (Data Layer Security)

Для предотвращения несанкционированного доступа и манипуляций через промпт-инжиниринг внедряются следующие механизмы:

**Context Hard-Coding (Запрет на инъекцию ID):** Идентификатор `internal_user_id` никогда не извлекается из текста сообщения или интента ИИ. Бэкенд принудительно инжектирует его из защищенного токена сессии.

**Database Scoping:** Каждый SQL-запрос к финансовым данным жестко ограничен фильтром `WHERE internal_user_id = $1`. Система технически не может выполнить запрос к данным другого пользователя в рамках текущей сессии.

**Row Level Security (RLS):** На уровне PostgreSQL включена политика RLS. Даже в случае ошибки в коде бэкенда, база данных на системном уровне скроет строки, не принадлежащие `app.current_user_id`.

**Составные ограничения (Compound Constraints):** Для критических таблиц (например, `pending_layer`) используются уникальные ключи на связку `(id, internal_user_id)`. Это исключает активацию чужих черновиков транзакций.


--------------------------------------------------------------------------------

# 4. Управление доступом и Домены данных

Данные распределены по трем изолированным доменам.

| Домен | Описание | Правило доступа |
| --- | --- | --- |
| User Domain | Личное финансовое пространство. | Доступ только у Root-владельца. |
| Shared Domain | Пространство команды или семьи. | Доступ согласно access_grants (RBAC). Проверка прав происходит на уровне БД через RLS. |
| Staging Domain | Буферная зона (Pending Layer). | Временное хранилище. Требует «Минимального волевого акта» для переноса в Ledger. |


--------------------------------------------------------------------------------

# 5. Когнитивная безопасность (AI Safety)

**Data Sanitization:** Перед отправкой в API Gemini/Claude данные очищаются от PII.

**Prompt Injection Protection:** Дирижёр оборачивает запрос пользователя в **System Prompt** с высшим приоритетом, блокируя попытки подмены команд или ID.

**Output Validation:** Ответы ИИ проходят через Rust-валидатор перед выполнением любых действий в системе.


--------------------------------------------------------------------------------

# 6. Приватность и Shadow Layer

**Shadow Transactions:** Транзакции с тегом `hidden` записываются в БД для баланса, но логически исключены из выборок для Shared-доменов.

**Инвариант:** В общих отчетах детали скрытых транзакций заменяются системной заглушкой, сохраняя верность итоговой суммы.


--------------------------------------------------------------------------------

# 7. Жизненный цикл и TTL (Data Lifecycle)

**Мгновенное уничтожение медиа:** Исходные фото чеков и аудио удаляются сразу после парсинга в JSON.

**Эфемерность Pending (TTL 10 дней):** Неподтвержденные записи в Staging Domain удаляются автоматически, предотвращая замусоривание.


--------------------------------------------------------------------------------

# 8. Логирование и Аудит (Audit Trail)

**Immutable Logs:** Запрет на `DELETE` транзакций в Ledger на уровне триггеров БД.

**System Audit Logs:** Отдельная таблица фиксирует все изменения системных настроек: изменение налоговых правил (`tax_rules`), выдачу прав доступа (`access_grants`) и смену лимитов.

**Маскирование:** Технические логи маскируют суммы и адреса кошельков для инженеров поддержки.


--------------------------------------------------------------------------------

# Итог:

Безопасность Sana — это многослойный фильтр, где **Backend** и **PostgreSQL RLS** выступают финальными арбитрами. Мы не доверяем тексту в чате; мы доверяем только подтвержденной сессии и жестким правилам доступа на уровне ядра данных.
