# DRAFT_Tables Schemas & Descrition

# АРХИТЕКТУРНАЯ КАРТА БАЗЫ ДАННЫХ SANA

Ниже представлен полный перечень таблиц, сгруппированных по функциональным слоям, который служит финальным техническим заданием для разработки Backend-части.

## 1. Слой Идентификации и Приватности (Identity Separation)

*Цель: Обеспечить разрыв связи между физической личностью и её деньгами.*

**auth_identities**: Единственный мост между внешними ID (Telegram/Email) и анонимным `internal_user_id`.

**users_metadata**: Зашифрованные персональные настройки, имя для ИИ и базовая валюта.


--------------------------------------------------------------------------------

## 2. Слой Финансовых Сущностей (The Mirror Layers)

*Цель: Отражение физической реальности (где деньги) и логических намерений (зачем деньги).*

**wallets**: Иерархическая структура физических счетов (Parent/Child Mirror) для банков, налички и крипто-активов.

**envelopes**: Приоритизированные логические конверты (цели, налоги, свободные траты).

**assets**: Контекстные якоря (авто, недвижимость), генерирующие расходы.

**obligations**: Учет долгов (Payable) и ожидаемых поступлений (Receivable).


--------------------------------------------------------------------------------

## 3. Ядро Реестра и Мультивалютность (The Immutable Core)

*Цель: Неизменяемый поток событий и точные курсы валют.*

**ledger_transactions**: Главная таблица системы. Хранит иммутабельную историю всех движений с детализацией до мерчанта, категории и пользовательских заметок.

**fx_rates_history**: История курсов валют (Minute-Precision) для исторической точности пересчета в базовую валюту.

**categories_dictionary**: Семантический справочник категорий и иконок.


--------------------------------------------------------------------------------

## 4. Слой Бизнес-Логики (Project P&L and Tax Engine)

*Цель: Изоляция экономики проектов и автоматизация налогов.*

**projects**: Описание бизнес-проектов или крупных целей.

**tax_rules**: Налоговые режимы (A, B, V) и ставки для авто-резервирования.

**project_balances**: Агрегированные P&L отчеты по каждому проекту в реальном времени.


--------------------------------------------------------------------------------

## 5. Когнитивный Слой и Интерфейс (AI Interaction)

*Цель: Управление контекстом диалога и подтверждение транзакций.*

**chat_sessions**: Сессии с привязкой к контексту (проект/глобал) и управлением временем жизни (TTL).

**chat_messages**: Полная мультимодальная история переписки (текст, фото чеков, аудио).

**pending_layer**: Буфер для подтверждения транзакций («Минимальный волевой акт»).


--------------------------------------------------------------------------------

## 6. Слой Производительности и Аналитики (Performance Layer)

*Цель: Мгновенные ответы ИИ без сканирования истории.*

**user_snapshots**: **Центральный Дашборд.** Агрегирует Net Worth, Safe-to-Spend, налоговые резервы и балансы всех счетов. Обновляется триггерами `PL/pgSQL` атомарно с Ledger.


--------------------------------------------------------------------------------

### Фундаментальные принципы работы структуры:

**Математическая чистота:** В любой момент времени ∑Wallets≡∑Envelopes.

**Иммутабельность:** Никаких `DELETE` или `UPDATE` в финансовых таблицах; только сторнирование.

**Атомарность:** Обновление состояния (Snapshot) происходит в той же транзакции, что и запись в реестр (Ledger).


--------------------------------------------------------------------------------

# 1. Слой Аутентификации и Идентификации (Identity Isolation)

*Эти таблицы отделены от финансового ядра для обеспечения приватности.*

## 1.1. Auth Identities:

Таблица **auth_identities** реализует концепцию **«Разрыва идентичности» (Identity Separation)**. Она является единственным шлюзом между внешним миром (вашим Telegram-аккаунтом или почтой) и анонимным финансовым ядром Sana.

Эта таблица относится к **Layer 1 (Public Auth)** и физически изолирована от финансовой логики Ledger.

### 1.1.1. Спецификация таблицы: `auth_identities`

| Имя поля | Описание и бизнес-логика | Примечания и безопасность |
| --- | --- | --- |
| internal_user_id | Анонимный UUID, используемый во всей системе (Ledger, Снапшоты). | Primary Key. Это единственная ссылка, связывающая личность с деньгами. |
| provider_type | Тип поставщика аутентификации (например, telegram, email, apple_id). | Позволяет одному пользователю иметь несколько способов входа. |
| external_id | Реальный идентификатор внешней системы (например, Telegram ID 12345678). | Никогда не передается в слои Ledger или AI-аналитики. |
| identity_hash | Хэш внешнего ID для быстрой и безопасной сверки. | Дополнительный слой защиты при поиске пользователя. |
| created_at | Дата и время первой регистрации в системе. | Техническая метка времени. |
| last_seen_at | Время последнего взаимодействия с сервисом. | Используется для управления TTL сессий и аналитики активности. |
| status | Статус аккаунта: active, blocked, deleted. | Позволяет мгновенно отозвать доступ к системе. |
| provider_metadata | JSONB-поле для данных провайдера (никнейм, имя, URL аватара). | Эти данные используются только для отображения в интерфейсе приветствия. |

### 1.1.2. Принципы безопасности и изоляции

**Identity Split (Разрыв связи):** Ни одна таблица в финансовом блоке (Ledger, Wallets, Envelopes) не содержит полей `telegram_id` или `email`. Они ссылаются только на анонимный `internal_user_id`.

**Zero Trust (Нулевое доверие):** Взлом базы данных Ledger не позволит злоумышленнику узнать, кому принадлежат эти деньги, так как связь хранится в этой отдельной таблице `auth_identities`, защищенной повышенными правилами доступа.

**Приватность для ИИ:** Когда Дирижёр передает запрос пользователя в LLM (Gemini/Claude), он извлекает из `provider_metadata` только имя пользователя (например, «Алексей»), но никогда не передает технические идентификаторы провайдеров.

**Смена провайдера:** Благодаря такой схеме, пользователь может легко сменить Telegram-аккаунт или привязать Email к своему `internal_user_id`, сохранив всю историю своих финансов нетронутой.


--------------------------------------------------------------------------------

## 1.2. User Meatadata:

Таблица **users_metadata** относится ко второму уровню защиты (Layer 2) и служит для хранения персональных настроек и личных данных в зашифрованном виде. Она изолирована от финансового реестра (Ledger), чтобы даже в случае утечки данных транзакций личность пользователя оставалась защищенной.

### 1.2.1. Спецификация таблицы: `users_metadata`

| Имя поля | Описание и бизнес-логика | Примечания и безопасность |
| --- | --- | --- |
| internal_user_id | Анонимный UUID пользователя. | Primary Key. Ссылка на анонимное ядро системы. |
| encrypted_display_name | Зашифрованное имя для обращения ИИ-агентов (например, «Алексей»). | Используется Агентами (Zen, Consigliere) для персонализации общения. |
| encrypted_legal_name | (Опционально) Полное юридическое имя. | Необходимо для генерации инвойсов и налоговых отчетов. |
| timezone | Часовой пояс пользователя. | Критично для работы Nostradamus и отправки уведомлений в нужное время. |
| base_currency | Основная валюта отображения (базовая валюта). | В этой валюте рассчитываются все показатели в Дашборде (Snapshot). |
| ui_preferences | Настройки интерфейса (язык, тема, формат даты). | JSONB-поле для гибкой настройки Web и App интерфейсов. |
| ai_settings | Предпочтения для ИИ (выбранный тон голоса, уровень детализации ответов). | Определяет, как именно Дирижёр будет инструктировать агентов (например, Sana Zen). |
| onboarding_status | Текущий шаг обучения пользователя в системе. | Позволяет системе дозированно вводить новые функции. |
| updated_at | Время последнего обновления метаданных. | Техническое поле для синхронизации. |

### 1.2.2. Принципы работы с метаданными пользователя

**Encryption at Rest:** Все персональные данные (имена, специфические предпочтения) шифруются на уровне приложения перед записью в базу данных.

**Изоляция для ИИ (Sanitization):** Когда Дирижёр запрашивает информацию, он извлекает только `encrypted_display_name` для передачи в LLM, оставляя остальные персональные данные внутри защищенного контура.

**Синхронизация с чатом:** Метаданные позволяют системе «узнавать» пользователя в разных каналах (Telegram, Web) и сохранять единый стиль общения.


--------------------------------------------------------------------------------

Важное архитектурное решение: > Данные из этой таблицы никогда не попадают в одну выборку (SQL Join) с таблицей ledger_transactions в аналитических запросах. Это гарантирует соблюдение принципа Identity Separation.

# 2. Слой Физического и Логического Состояния (The Balance)

*Обеспечивает соблюдение уравнения *∑Wallets=∑Envelopes*.*

## 2.1. User Accounts:

Таблица **wallets** (или `accounts`) реализует иерархическую модель «Родитель — Ребенок», которая позволяет системе Sana эффективно управлять сложными финансовыми структурами, такими как криптокошельки с множеством токенов или мультивалютные банковские счета.

Эта структура минимизирует когнитивный шум: пользователь видит «Метамаск» как единую сущность, в то время как Ledger ведет учет каждой монеты на отдельном дочернем счете.

### 2.1.1. Спецификация таблицы: `wallets`

| Имя поля | Описание и бизнес-логика | Примечания |
| --- | --- | --- |
| id | Уникальный UUID кошелька. | Первичный ключ. |
| internal_user_id | Ссылка на анонимный ID пользователя. | Обеспечивает разрыв идентичности. |
| parent_id | Ссылка на id родительского кошелька (самоссылка). | Если NULL — это Parent Wallet (Физ. уровень). Если заполнено — это Child Mirror (Уровень актива). |
| name | Имя счета (например, «MetaMask», «BTC», «Каспи»). | Отображаемое название для пользователя и ИИ. |
| wallet_type | Тип: physical_device, crypto_software, exchange, fiat_bank, cash. | Помогает ИИ понимать контекст (например, где нужны ключи, а где — логин). |
| currency_code | Код основного актива счета (USD, BTC, KGS и т.д.). | Для родительских счетов может быть системным маркером (например, MULTI). |
| is_system_account | Флаг того, что это виртуальный счет «General Ledger». | Используется по умолчанию, если другие счета не добавлены. |
| is_active | Флаг активности счета. | Позволяет архивировать закрытые счета без удаления истории в Ledger. |
| metadata | JSONB-поле (адреса контрактов, публичные ключи, реквизиты банка). | Хранит технические детали, специфичные для провайдера. |

## 2.2. Envelopes:

Таблица **envelopes** (Конверты) определяет логическую архитектуру ваших финансов. В то время как кошельки (`wallets`) отвечают на вопрос «Где лежат деньги?», конверты отвечают на вопрос «Зачем они там лежат?».

Введение **приоритизации** позволяет системе Sana и ее ИИ-агентам автоматически распределять входящие потоки и давать советы по оптимизации бюджета в реальном времени.

### 2.2.1. Спецификация таблицы: `envelopes`

| Имя поля | Описание и бизнес-логика | Примечания |
| --- | --- | --- |
| id | Уникальный UUID конверта. | Первичный ключ. |
| internal_user_id | Ссылка на анонимный ID пользователя. | Обеспечивает разрыв идентичности. |
| name | Имя конверта (Еда, Аренда, Налоги, На монитор). | Используется ИИ для общения с пользователем. |
| priority | Числовой индекс приоритета (например, 1–100). | Чем выше число, тем важнее наполнить этот конверт первым. |
| envelope_type | Тип: obligation (Обязательство), reserve (Резерв), saving (Цель), free_spend (Свободные), system_residue (Остаток). | Помогает Nostradamus прогнозировать кассовые разрывы. |
| target_amount | Целевая сумма (например, $1,200 для аренды или $1,000 для монитора). | Используется для расчета прогресса и «Safe-to-Spend». |
| parent_id | Ссылка на родительский конверт (для иерархии). | Позволяет создавать группы (например, «Семья» -> «Дети»). |
| is_active | Флаг активности конверта. | Деактивированные конверты не участвуют в новых распределениях. |
| metadata | JSONB-поле: иконка, цвет, специфические правила ИИ. | Хранит визуальные настройки и тон общения Агента Zen. |

## 2.3. Assets:

Таблица **assets** в системе Sana выступает в роли «контекстного якоря». В отличие от классических систем учета, мы не отслеживаем рыночную стоимость автомобиля или квартиры. Для нас актив — это сущность, которая генерирует расходы и требует планирования, что позволяет ИИ-агентам и модулю **Nostradamus** строить более точные прогнозы на основе владения.

### 2.3.1. Спецификация таблицы: `assets`

| Имя поля | Описание и бизнес-логика | Примечания |
| --- | --- | --- |
| id | Уникальный UUID актива. | Первичный ключ. |
| internal_user_id | Ссылка на анонимный ID пользователя. | Обеспечивает разрыв идентичности. |
| name | Имя актива (например, «Tesla Model 3», «Квартира на Ленина»). | Используется ИИ для уточнения контекста трат. |
| asset_type | Тип: vehicle (Транспорт), real_estate (Недвижимость), equipment (Техника), other. | Помогает классифицировать расходы (налоги, ТО, коммуналка). |
| is_active | Флаг владения активом. | Если false, актив считается проданным, но история трат на него сохраняется. |
| metadata | JSONB-поле для технических деталей (VIN, адрес, дата следующего ТО). | Хранит данные для предиктивной аналитики Nostradamus. |
| created_at | Время добавления актива в систему. | Техническое поле. |

## 2.4. Data Obligations Structure:

Документ для таблицы **obligations** (Обязательства) завершает описание логического слоя системы. В Sana долги — это не «минус» на балансе, а параллельная финансовая реальность.

Здесь обязательства разделены по направлению (нам должны / мы должны) внутри одной таблицы. Это позволит системе одним запросом строить полную карту финансовых связей, включая проектные дебиторки и личные займы.

### 2.4.1. Концепция: Два вектора обязательств

Вместо отрицательных остатков в кошельках, Sana использует два типа записей:

**Receivable (Нам должны):** Это «виртуальный актив». Например, клиент еще не оплатил проект, или вы одолжили другу $100. Это обещание прихода денег в будущем.

**Payable (Мы должны):** Это «виртуальное списание». Например, кредит в банке или остаток оплаты верстальщику после сдачи проекта. Эти средства фактически находятся в вашем кошельке, но «логически» они вам уже не принадлежат.

**А. Взаимодействие с физическим миром:**

**Б. Проектный контекст (Пример: ИП):**

Как видно в сценарии с проектом «Логотип»:

Система фиксирует поступление $2,000.

**Результат:** ИИ вычитает это обязательство из текущего остатка, чтобы показать пользователю его **Чистую прибыль** ($1,380) в реальном времени.

**В. Роль для ИИ-агентов:**

Благодаря этой таблице, вопрос пользователя *«Кто и сколько мне должен?»* не требует поиска по истории сообщений. Дирижёр просто делает выборку из таблицы `obligations` со статусом `active` и типом `receivable`.

### 3.1.2. Технические Инварианты Реестра (Ledger)

**Иммутабельность (Запрет на DELETE/UPDATE):** На уровне базы данных через триггеры физически запрещено удалять или изменять строки в таблице `ledger_transactions`. Любое исправление ошибки осуществляется только через новую запись (метод сторнирования), что гарантирует вечную и проверяемую историю.

**Атомарное обновление Snapshot:** Успешная вставка строки в реестр автоматически инициирует триггер `PL/pgSQL` для обновления таблицы `user_snapshots`. Это гарантирует, что Дашборд и ИИ-агенты всегда оперируют актуальными агрегированными данными.

**Дефолтный счет (System Account):** Если пользователь еще не детализировал свои физические счета, система автоматически использует виртуальный счет **«General Ledger»**.

Анонимизация и Субъектность: Поле wallet_id служит мостом к физической реальности. Использование System Account позволяет вести учет «в вакууме», если пользователь не хочет добавлять реальные банки в базу, сохраняя при этом математическую точность и инвариант баланса:

∑Envelopes=∑Wallets

### 3.1.3. Когнитивная Обработка и Извлечение Смыслов

**AI Custom Notes (Автоматическое извлечение):** Поле `user_note` заполняется **Агентом-Парсером** (Vision/Audio/Text) в момент обработки входящего сообщения. ### 3.1.4. Приватность и Структура Данных

**Категории vs Конверты:** Система строго разделяет эти понятия:**Конверт (Envelope):** Это *цель или источник* средств (Налоги, Накопления, Еда).**Категория/Подкатегория:** Это *свойство* самой транзакции.*Пример:* Вы тратите деньги из конверта «Семья» на категорию «Продукты» в магазине «Magnum».

## 3.2. Transaction Tags:

Для того чтобы система оставалась гибкой и поддерживала глубокую аналитику ИИ, мы разделили классификацию на **два уровня**: «Словарный запас» (Справочники) и «Живое использование» (Метки в Ledger).

Учитывая, что в `ledger_transactions` мы уже внедрили поля `category_slug` и `subcategory_slug`, нам не нужно делать таблицу тегов единственным местом хранения категорий. Вместо этого мы создаем **Семантические Справочники**.

### 3.2.1. Решение: Разделение на Справочники и Теги

Мы разделяем структуру на три таблицы, чтобы отделить системную таксономию (категории) от пользовательской фолксономии (теги).

### 3.2.2. Таблица: `categories_dictionary` (Таксономия)

### 3.2.4. Почему это лучше, чем одна общая таблица тегов?

**Чистота Ledger:** В основной таблице транзакций остаются только короткие `slug` (строки). Это делает Ledger быстрым и легким для математических расчетов.

**Семантическая гибкость:** Вы можете изменить название категории с «Еда» на «Пропитание» или поменять иконку в одном месте (`categories_dictionary`), и это мгновенно обновится во всем интерфейсе, не затрагивая миллионы записей в Ledger.

**Обучение ИИ:** Таблица `merchant_profiles` позволяет Дирижёру «узнавать» места. Если система видит мерчанта «Netflix», она сразу знает, какой `category_slug` подставить, основываясь на справочнике.

**Shadow Layer и Спец-теги:** Теги типа `hidden` остаются в Ledger как управляющие флаги, но в `tags_metadata` вы можете прописать для них особые правила отображения (например, «не показывать в семейном доступе»).

Она позволяет системе Sana мгновенно восстанавливать финансовую картину любого момента в прошлом и поддерживать мульти-валютность без потерь на округлении или рыночных скачках.

### 3.3.2. Принципы работы с курсами валют

**Minute-Precision (Минутная точность):** Воркеры Бэкенда опрашивают внешние API с высокой частотой, чтобы в таблице всегда была актуальная котировка для любой транзакции, совершаемой «сейчас».

**Snapshot на лету:** Когда пользователь записывает транзакцию (например, покупку кофе за 450 сомов), Бэкенд находит в этой таблице самую свежую запись для пары `USD/KGS` и копирует это значение в поле `fx_rate_snapshot` основной таблицы Ledger.

**Provider Agnostic (Независимость от провайдеров):** Благодаря полю `provider_slug`, система может легко переключаться между источниками (например, брать курсы фиата из Fixer.io, а крипты — из CoinGecko), не меняя структуру данных.

**Failover-резервирование:** Если основной провайдер (например, Binance) недоступен, система берет курс от резервного (например, Coinbase) и помечает это в логах для последующего аудита.

# 4. Слой Бизнес-Логики и Проектов

## 4.1. Projects:

Таблица **projects** — это верхнеуровневый слой управления в Sana, который превращает обычный учет расходов в полноценную систему управления бизнесом или крупными целями. Проект выступает как «контейнер смыслов», объединяющий транзакции, налоги, долги и аналитику в единую экономическую единицу.

### 4.1.1. Спецификация таблицы: `projects`

--------------------------------------------------------------------------------

### 4.1.2. Бизнес-логика и системные связи

**1. Изоляция P&L (Profit and Loss):**

Каждый проект в Sana — это «остров экономики». Благодаря связи `ledger_transactions` с `project_id`, система мгновенно вычисляет **Чистую прибыль** проекта, автоматически вычитая из дохода налоги и обязательства перед подрядчиками.

**2. Проектный Налоговый Резерв:**

Проекты могут иметь свои собственные настройки в **Tax Engine**. Например, для одного проекта налоги могут резервироваться по ставке 6% (ИП), а для другого — не резервироваться вовсе (личный проект).

**3. Связь с Обязательствами:**

Проекты часто включают в себя авансы и отложенные платежи. Таблица `obligations` ссылается на `project_id`, позволяя ИИ отвечать на вопросы типа: *«Какой чистый доход по всем проектам за квартал?»*, учитывая еще не выплаченные, но зафиксированные долги.

**4. Когнитивный контекст для Дирижёра:**

Если пользователь пишет: *«Пришло 2000 за Логотип»*, Дирижёр находит активный проект с таким именем и автоматически привязывает транзакцию к нему, запуская цепочку создания налоговых резервов и фиксации обязательств.


--------------------------------------------------------------------------------

## 4.2. Tax Rules:

Таблица **tax_rules** является управляющим центром для **Tax Engine**. Она определяет, какую логику применять при поступлении средств на конкретный счет или в рамках конкретного проекта. Эта таблица позволяет системе Sana автоматически превращать «грязный доход» в «чистую прибыль» без участия пользователя.

### 4.2.1. Спецификация таблицы: `tax_rules`

| Имя поля | Описание и бизнес-логика | Примечания |
| --- | --- | --- |
| id | Уникальный UUID правила. | Первичный ключ. |
| internal_user_id | Ссылка на анонимный ID пользователя. | Обеспечивает изоляцию налоговой логики. |
| project_id | (Опционально) Ссылка на конкретный проект. | Правило применяется ко всем транзакциям этого проекта. |
| wallet_id | (Опционально) Ссылка на физический кошелек. | Правило применяется к любому доходу, упавшему на этот счет (например, на карту ИП). |
| tax_mode | Режим: A (Процент), B (Доход-Расход), V (Ручной/Откл). | Определяет алгоритм функции fn_calculate_tax_reserve. |
| tax_rate | Налоговая ставка (например, 0.06 для 6%). | Числовой коэффициент для автоматического резервирования. |
| tax_envelope_id | ID конверта, куда будут резервироваться налоги. | Обычно это системный конверт «Налоги». |
| is_active | Флаг активности правила. | Позволяет временно отключать авто-резервирование. |
| metadata | JSONB-поле для специфических условий и лимитов. | Хранит исключения или дополнительные формулы. |

### 4.2.2. Режимы налогообложения (A, B, V)

Система Sana поддерживает три эволюционных подхода к расчету налогов, которые выбираются в поле `tax_mode`:

**Режим A (Percentage-based):** Самый простой и эффективный для ИП. Любое поступление умножается на `tax_rate`, и сумма мгновенно уходит в налоговый конверт.

**Режим B (Profit-based / Доход минус Расход):** Функция `fn_apply_tax_deduction` анализирует связанные расходы по проекту и пересчитывает налогооблагаемую базу в реальном времени.

**Режим V (Manual / Verification):** Система не делает авто-резервирования, но ИИ-агент **Consigliere** напоминает пользователю о необходимости ручного распределения или подтверждения суммы.


--------------------------------------------------------------------------------

### 4.2.3. Системные инварианты Tax Engine

**Приоритет проекта:** Если транзакция привязана к проекту, система использует `tax_rule`, связанное с этим проектом, игнорируя общее правило кошелька.

**Атомарность резерва:** Создание записи в `ledger_transactions` (Доход) и создание связанной записи (Налоговый резерв) происходит внутри одной транзакции базы данных через `fn_create_transaction`.

**Прозрачность для ИИ:** Благодаря этой таблице, ИИ может мгновенно объяснить пользователю: *«Я отложила $120, так как по проекту 'Логотип' у тебя настроен налог 6%»*.

## 4.3. Project Balances Aggregation:

Таблица **project_balances** представляет собой слой агрегации, который превращает тысячи строк транзакций в понятную бизнес-метрику. Это «финансовый пульс» каждого вашего начинания, позволяющий ИИ-агентам мгновенно отвечать на вопросы о прибыльности без пересчета всего реестра.

Данная таблица является ключевой частью модуля **Project-Based P&L** и обновляется автоматически при каждом движении средств, связанных с `project_id`.

### 4.3.1. Спецификация таблицы: `project_balances`

| Имя поля | Описание и бизнес-логика | Примечания |
| --- | --- | --- |
| project_id | Уникальный ID проекта. | Primary Key. Связь с таблицей projects. |
| internal_user_id | Анонимный ID пользователя. | Обеспечивает изоляцию данных. |
| total_income | Сумма всех поступлений по проекту в базовой валюте. | Грязный доход (Revenue). |
| total_expenses | Сумма всех фактических трат по проекту. | Прямые расходы. |
| tax_reserved | Общая сумма налогов, отложенных в резерв для этого проекта. | Вычисляется Tax Engine автоматически. |
| pending_payables | Сумма невыплаченных обязательств перед подрядчиками. | Берется из таблицы obligations с типом payable. |
| pending_receivables | Сумма ожидаемых поступлений от клиентов по проекту. | Берется из таблицы obligations с типом receivable. |

### 4.3.2. Механика работы и инварианты

**Триггерное обновление:** Таблица не заполняется вручную. Каждая запись в `ledger_transactions`, содержащая `project_id`, вызывает триггер `PL/pgSQL`, который пересчитывает агрегаты в `project_balances`.

**Изоляция потоков:** Даже если вы оплачиваете аренду офиса и верстальщика с одной и той же карты, `project_balances` разделит эти сущности, оставив в проекте только то, что помечено его ID.

**Прогнозная аналитика:** На основе `net_profit` и `pending_receivables` модуль **Nostradamus** может предсказать кассовый разрыв именно в рамках бизнеса, даже если личный бюджет пользователя в порядке.

### 4.3.3. Роль в интерфейсе и для ИИ

Благодаря этой таблице, взаимодействие пользователя с Sana выглядит как диалог с опытным финдиректором:

**Запрос пользователя:** *«Какой чистый доход по всем проектам за квартал?»*

**Действие ИИ:** Дирижёр просто суммирует поле `net_profit` из `project_balances` для активных проектов.

**Результат:** Пользователь мгновенно получает цифру: *«Твоя чистая прибыль составляет $1,380»*.

## 5.3. Pending Layer:

Таблица **pending_layer** является «карантинной зоной» системы Sana. Она реализует критически важный принцип **«Минимального волевого акта»**, гарантируя, что ни одна транзакция, извлеченная ИИ, не попадет в неизменяемый Ledger без осознанного подтверждения пользователем.

Этот слой защищает математическую целостность реестра от «галлюцинаций» нейросети или случайных интерпретаций.


--------------------------------------------------------------------------------

### 5.3.1. Спецификация таблицы: `pending_layer`

| Имя поля | Описание и бизнес-логика | Примечания |
| --- | --- | --- |
| id | Уникальный UUID записи-кандидата. | Первичный ключ. |
| internal_user_id | Ссылка на анонимный ID пользователя. | Изолирует черновики транзакций. |
| message_id | Ссылка на сообщение в chat_messages. | Позволяет кнопкам «Подтвердить» в чате знать, какую запись активировать. |
| proposed_data | JSONB-объект со всеми полями будущей транзакции. | Содержит: amount, currency, wallet_id, envelope_id, merchant, category, user_note. |
| status | Статус: pending (ожидает), confirmed (подтвержден), rejected (отклонен), expired (истек). | Управляет жизненным циклом черновика. |
| confidence_score | Уровень уверенности ИИ в распознавании (0.0 – 1.0). | Если скор низкий, Дирижёр подсветит поля, требующие особого внимания. |
| created_at | Время создания черновика. | Используется для расчета TTL. |
| expires_at | Время автоматического удаления черновика. | Очищает базу от забытых или неактуальных подтверждений. |
| metadata | JSONB-поле: обоснование ИИ (почему выбрана эта категория), ссылки на фрагменты чека. | Помогает пользователю понять логику системы перед подтверждением. |

### 5.3.2. Механика «Минимального волевого акта»

**Формирование гипотезы:** Когда пользователь присылает сообщение или фото чека, ИИ-агенты формируют «гипотезу транзакции» и записывают её в `pending_layer`.

**Визуализация:** Система выводит пользователю карточку с кнопками «Да, записать» или «Редактировать».

**Активация (Promote to Ledger):** Только после нажатия «Да», данные из `proposed_data` переносятся в таблицу `ledger_transactions`, становясь частью неизменяемой истории.

**Соблюдение инварианта:** До момента подтверждения записи в `pending_layer` никак не влияют на балансы кошельков и конвертов. Уравнение ∑Wallets=∑Envelopes проверяется только в момент переноса данных в Ledger.

### 5.3.3. Роль для ИИ и интерфейса

**Право на ошибку:** Пользователь может отклонить неверно распознанную транзакцию, не создавая «мусорных» записей в основном реестре.

**Групповые операции:** Если в одном сообщении было несколько транзакций (например, «купил кофе, хлеб и оплатил интернет»), в `pending_layer` создается несколько записей с одним `message_id`, которые можно подтвердить одним кликом.

**Shadow Layer Pre-check:** Если транзакция помечена как скрытая (`hidden`), она все равно проходит через `pending_layer`, чтобы пользователь подтвердил её приватный статус.

# 6. Слой Мгновенного Состояния (The Dashboard Engine)

*Таблица-зеркало для мгновенного доступа ИИ к агрегированным данным.*

## 6.1. User Snapshots:

Таблица **user_snapshots** является «Dashboard Engine» — высокопроизводительным слоем, который агрегирует данные из всех финансово-смысловых таблиц в одну запись. Она служит «единым окном» для ИИ-агентов, позволяя им мгновенно получать финансовый контекст пользователя без выполнения тяжелых аналитических SQL-запросов к миллионам строк `ledger_transactions`.

### 6.1.1. Спецификация таблицы: `user_snapshots`

| Имя поля | Описание и бизнес-логика | Примечания и источники данных |
| --- | --- | --- |
| internal_user_id | Анонимный UUID пользователя. | Primary Key. Связь с анонимным ядром. |
| net_worth_base | Общий капитал: Сумма всех активов минус обязательства. | Рассчитывается в базовой валюте пользователя. |
| safe_to_spend | Безопасный остаток: Свободные деньги за вычетом приоритетных конвертов. | Реальная ликвидность для трат «здесь и сейчас». |
| total_tax_reserve | Общая сумма во всех налоговых конвертах пользователя. | Позволяет ИИ сразу сказать, сколько отложено на налоги. |
| crypto_valuation | Суммарная стоимость всех крипто-активов в базовой валюте. | Агрегат по всем Child Mirror Wallets (BTC, ETH и т.д.). |
| wallets_summary | JSONB: Список текущих балансов по всем физическим счетам. | Включает ID, имя счета и текущий остаток. |
| envelopes_summary | JSONB: Распределение средств по всем логическим конвертам. | Позволяет видеть прогресс накоплений и лимиты. |
| obligations_summary | JSONB: Общие суммы дебиторской и кредиторской задолженности. | total_receivable и total_payable в одном поле. |
| projects_pnl | JSONB: Краткий статус прибыли по активным проектам. | Содержит net_profit по каждому project_id. |
| last_ledger_id | ID последней транзакции, учтенной в этом снапшоте. | Для контроля синхронизации с основным реестром. |
| updated_at | Время последнего обновления (Trigger Execution Time). | Гарантирует актуальность данных «до секунды». |

### 6.1.2. Механика обновления и атомарность

**PL/pgSQL Triggers:** Обновление происходит на уровне базы данных. Любой `INSERT` в `ledger_transactions` запускает функцию, которая пересчитывает снапшот.

**Атомарность:** Обновление снапшота и запись в Ledger происходят в одной транзакции. Если снапшот не обновился, транзакция в Ledger откатывается, что предотвращает расхождение данных.

**Инвариант Баланса:** В снапшоте всегда проверяется равенство ∑Wallets≡∑Envelopes. Если оно нарушено, система сигнализирует о «Пробеле в Знании».

### 6.1.3. Применение в ИИ-агентах

Благодаря этой таблице, Дирижёр при каждом запросе пользователя отправляет ИИ-агенту (например, **Sana Zen**) компактный контекст:

«Контекст: На счетах $4,500. Обязательства на $4,000 (Аренда, Налоги). Safe-to-Spend: $500».

Это позволяет ИИ отвечать на сложные вопросы мгновенно:

**Пользователь:** *«Какая прибыль по проектам в этом месяце?»*

**ИИ:** (Считывает поле **projects_pnl**) — *«Чистая прибыль в этом месяце: $3,305»*.
