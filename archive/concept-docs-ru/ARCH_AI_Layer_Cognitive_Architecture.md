Этот документ описывает архитектуру искусственного интеллекта системы Sana. Когнитивный слой не является монолитом, а разделен на два независимых контура: **Входящий (Ingestion)** и **Исходящий (Egestion)**. Каждый контур управляется своим Дирижёром и набором агентов, что обеспечивает двунаправленную контекстную целостность.

**Статус:** Final Cognitive Architecture **Принцип:** «Двухтактный цикл». Сначала понимаем смысл, потом формируем реакцию. **Роль Backend:** Оркестратор и держатель контекста. ИИ никогда не ходит в БД напрямую.


--------------------------------------------------------------------------------

# 1. Архитектурный Пайплайн (The Dual-Loop Pipeline)

Процесс обработки сообщения представляет собой замкнутую петлю, где Backend выступает в роли «челнока», переносящего данные между пользователем, Дирижёрами, Агентами и Базой Данных.

## Полный цикл обработки:

`User` -> `Frontend` -> `Backend` -> `Input Conductor` -> `Backend` -> `Input Agent` -> `Backend` -> `DB Function` -> `DB` -> `DB Function` -> `Backend` -> `Output Conductor` -> `Backend` -> `Output Agent` -> `Backend` -> `Frontend` -> `User`


--------------------------------------------------------------------------------

# 2. Контур 1: Клиент -> Сервис (Ingestion Layer)

Задача этого слоя — превратить хаос человеческого ввода (текст, голос, фото) в строгую структуру данных для Ledger.

## Шаг 1: Формирование контекста (Backend -> Input Conductor)

Получив сообщение от пользователя, Backend не отправляет его сразу на исполнение.

**Обезличивание:** Сообщение избавляется от всех идентификаторов в которое обёрнуто сообщение и присваивает ему uuid пользователя внутри системы.

**Сбор пула:** Backend извлекает из кэша (Redis/DB) короткий пул последних сообщений (Short Message Pool), чтобы понять, является ли новое сообщение продолжением предыдущего диалога.

**Запрос:** Backend отправляет этот пул + новое сообщение **Входящему Дирижёру**.

## Шаг 2: Маршрутизация и Запрос данных (Input Conductor)

Дирижёр анализирует контекст, но **не выполняет задачу сам**.

**Выбор Агента:** Он определяет, кто лучше справится: `Vision Parser` (если есть фото), `Voice Transcriber` (аудио) или `Text Normalizer`.

**Запрос информации:** Если для понимания не хватает данных (например, пользователь написал «положи на *тот самый* проект»), Дирижёр возвращает Бэкенду инструкцию: *«Мне нужен список активных проектов пользователя»*.

## Шаг 3: Обогащение и Исполнение (Backend -> Input Agent)

**Обогащение:** Backend выполняет запрос Дирижёра, достает нужные метаданные из БД.

**Вызов Агента:** Backend формирует окончательный пакет (Сообщение + История + Метаданные проектов) и передает его выбранному **Входящему Агенту**.

**Результат:** Агент возвращает структурированный JSON-интент (сумма, валюта, category_slug, wallet_id).

## Шаг 4: Фиксация (Backend -> DB)

Backend валидирует JSON и вызывает детерминированную PL/pgSQL функцию (`fn_create_transaction`), которая меняет состояние Ledger.


--------------------------------------------------------------------------------

# 3. Контур 2: Сервис -> Клиент (Egestion Layer)

Задача этого слоя — превратить сухой ответ базы данных (JSON result) в эмпатичный человеческий ответ, сохранив роль «Финансового ассистента».

## Шаг 1: Анализ результата (Backend -> Output Conductor)

База данных вернула результат (например, `new_balance: 500`, `status: success`, `tax_reserved: 30`).

**Запрос:** Backend передает этот результат и обновленный пул сообщений **Исходящему Дирижёру**.

## Шаг 2: Выбор Голоса (Output Conductor)

Дирижёр решает, *как* и *кем* ответить пользователю.

Если есть риск кассового разрыва -> Выбирается агент **Sana Zen** (поддержка).

Если успешная транзакция -> Выбирается агент **Consigliere** (отчет).

Если нужен сложный анализ -> Дирижёр просит Backend: *«Дай мне данные по расходам за прошлый месяц для сравнения»*.

## Шаг 3: Генерация ответа (Backend -> Output Agent)

**Обогащение:** Backend собирает запрошенную аналитику.

**Вызов Агента:** Выбранный агент получает: Результат операции + Контекст диалога + Доп. аналитику.

**Синтез:** Агент генерирует финальный текстовый ответ (например: *«Записала. Кстати, ты потратил на кофе меньше, чем обычно»*).

# 4. Безопасность данных (Data Ephemerality & Transit Security)

В отличие от стандартных подходов, Sana отдает приоритет **точности распознавания** над пре-модерацией входящего потока, компенсируя риски строжайшей политикой хранения.

## 4.1. Транзитная чистота (High-Fidelity Transit)

**Raw Input:** Система **не модифицирует** и не маскирует входящий поток (текст чеков, аудио, сообщения) до момента попадания к Агенту-Парсеру.

**Обоснование:** Любая попытка «зазвездить» данные (PII) до парсинга может разрушить семантику чека или исказить сумму/название мерчанта, что недопустимо для финансового инструмента. Точность должна быть 100%.

## 4.2. Identity Split (Разрыв Идентичности)

Безопасность транзита обеспечивается полной анонимностью метаданных запроса:

**Anonymous UUID:** В payload, уходящем к LLM-агентам, передается **только** анонимный `internal_user_id`,.

**Изоляция:** Агент видит «Текст чека» и «UUID», но физически не может связать это с Telegram ID, номером телефона или Email пользователя, так как эти данные хранятся в изолированном Auth-слое.

## 4.3. Политика Нулевого Следа (Zero-Persistence Policy)

**Мгновенное уничтожение:** Как только Backend получает от Агента валидный JSON-интент, исходные медиа-файлы (фото чеков, аудио) и сырой текст сообщения **физически удаляются** из оперативной памяти и S3-хранилищ.

**Результат:** Даже если злоумышленник перехватит данные постфактум, он найдет только сухие финансовые записи в Ledger, но не исходные фото или голосовые сообщения пользователя.

# 5. Механика Контекстной Целостности (The Short Pool)

Чтобы пользователь чувствовал, что общается с живым ассистентом, а не с командной строкой, используется механизм «Скользящего окна»:

**Короткий пул:** Backend при каждом такте передает Дирижёру последние N сообщений.

**Эффект:** Это позволяет Дирижёру понимать местоимения и отсылки.*Пользователь:* «Сколько я потратил на еду?»*Sana:* «500$».*Пользователь:* «А на такси?» (Backend передает историю -> Дирижёр понимает, что контекст вопроса — «траты за тот же период», но категория другая).

*Пользователь:* «Сколько я потратил на еду?»

*Sana:* «500$».

*Пользователь:* «А на такси?» (Backend передает историю -> Дирижёр понимает, что контекст вопроса — «траты за тот же период», но категория другая).

**Stateless Agent:** Сами Агенты (Sana Zen, Parser) остаются stateless (без состояния). Всю необходимую память им «впрыскивает» Backend в момент вызова по инструкции Дирижёра.

### Резюме

Новый пайплайн Sana реализует принцип **«Умного посредника»**. Backend здесь — это неутомимый курьер, который бегает между «мозгом» (Дирижёры), «руками» (Агенты) и «сейфом» (БД), гарантируя, что каждая сторона получает ровно столько информации, сколько нужно для работы, и ни байтом больше.
