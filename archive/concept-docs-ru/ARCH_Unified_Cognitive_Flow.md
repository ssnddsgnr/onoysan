# 1. Архитектурный Обзор: Двойная Петля (The Dual-Loop)

Процесс обработки любого сообщения пользователя в Sana не линеен, а цикличен. Он разделен на две независимые фазы, разделенные барьером детерминизма (Базой Данных):

**Ingestion Loop (Входящая петля):** Превращение хаоса (естественный язык/медиа) в порядок (JSON-транзакция в Ledger).*Цель:* Понять намерение и изменить состояние системы.

*Цель:* Понять намерение и изменить состояние системы.

**Egestion Loop (Исходящая петля):** Превращение порядка (результат SQL-запроса) в эмпатию (ответ на естественном языке).*Цель:* Интерпретировать изменение состояния для пользователя.

*Цель:* Интерпретировать изменение состояния для пользователя.

**Backend (sana-core)** выступает в роли Держателя Контекста (Context Holder) и Оркестратора, гарантируя, что «Интерпритатор» (AI) и «Память» (DB) никогда не встречаются напрямую.

# 4. Механизмы Безопасности Потока

## 4.1. Транзитная Чистота (High-Fidelity Transit)

Система **не модифицирует** входящие данные (OCR чека, аудио) до момента попадания к Агенту-Парсеру. Это гарантирует 100% точность распознавания. Безопасность обеспечивается тем, что эти данные живут в оперативной памяти секунды и никогда не сохраняются в БД в сыром виде.

## 4.2. Short Message Pool (Скользящее окно)

Backend хранит и передает Дирижёрам только последние N сообщений. Это позволяет Агентам понимать местоимения («оплати *это* с карты»), но предотвращает переполнение контекстного окна LLM и «галлюцинации» на устаревших данных.

## 4.3. Асинхронный Буфер (Pending Layer)

Если на шаге 1.3 Агент не уверен в данных (Confidence Score < 0.8), Backend прерывает цепочку записи в Ledger.

Вместо `fn_create_transaction`, данные пишутся в таблицу `pending_layer`.

Петля Выхода (Egestion) в этом случае формирует вопрос: *«Я поняла сумму, но не уверена насчет категории. Это 'Офис' или 'Дом'?»*.

# 5. Сводная диаграмма потока

```
sequenceDiagram
    participant User
    participant Backend as sana-core
    participant AI_Input as Input Conductor/Agent
    participant DB as PostgreSQL
    participant AI_Output as Output Conductor/Agent

    User->>Backend: Сообщение / Фото (MVA)
    Backend->>Backend: Sanitization & Identity Injection
    Backend->>AI_Input: Запрос (Msg + Short History)
    AI_Input->>Backend: JSON Intent (Normalized)
    Backend->>Backend: Intent Validation

    alt Validation Success
        Backend->>DB: CALL fn_create_transaction()
        DB-->>Backend: Transaction Result + Snapshot

        Backend->>AI_Output: Результат + Контекст
        AI_Output-->>Backend: Человеческий ответ (Sana Zen)
        Backend->>User: Ответ
        Backend->>Backend: Zero-Persistence Cleanup
    else Low Confidence
        Backend->>DB: INSERT INTO pending_layer
        Backend->>User: Вопрос на уточнение
    end
```

# Резюме

Архитектура **Unified Cognitive Flow** реализует принцип «Умного посредника». Backend здесь — это курьер, который бегает между «мозгом» (ИИ), «руками» (Парсеры) и «сейфом» (БД), гарантируя, что каждая сторона получает ровно столько информации, сколько нужно для работы, и ни байтом больше.
