Документ синтезирует архитектуру ядра (`sana-core`), систему спутников, шлюз мессенджера и слой адаптеров. Документ закрепляет роль Бэкенда как **Исполнительного Директора**, управляющего ресурсами, безопасностью и логистикой, делегируя математическую истину в PostgreSQL, а когнитивную интерпретацию — в AI-слой.

# 1. Философия: Исполнительная Власть

Backend Sana — это не монолит, выполняющий бизнес-логику, а высокопроизводительный **Оркестратор**.

**PostgreSQL:** Законодательная власть. Хранит инварианты, считает балансы, налоги и обеспечивает атомарность (PL/pgSQL).

**Rust Core:** Исполнительная власть. Управляет логистикой данных, защищает периметр, координирует ИИ и внешние сервисы.

**Принцип:** «Stateless & Fearless». Ядро не хранит состояние (оно в БД/Redis) и автоматически перезапускает упавшие компоненты.

# 2. Центральный Процесс: sana-core (The Master)

Монолитный процесс на Rust, спроектированный для асинхронной обработки тысяч соединений.

## 2.1. Sanitary Gateway (Шлюз-Цензор)

Единственная точка входа в систему. Реализует политику **Zero Trust**:

**Identity Injection:** Бэкенд извлекает `auth_token`, находит соответствующий `internal_user_id` и принудительно внедряет его в контекст запроса. Вглубь системы попадает только анонимный UUID.

**Schema Validation:** Валидация всех входящих JSON-интентов (от ИИ или клиента) на строгое соответствие типам перед обращением к БД.

## 2.2. Cognitive Logistics (Когнитивная Логистика)

Бэкенд реализует протокол **«Dynamic Context Assembly»**, где данные подгружаются лениво (lazy loading) по требованию интеллекта.

**Протокол обработки:**

**Ingestion (Первичный контекст):**Бэкенд получает сообщение пользователя.Обогащает его **Краткой Историей** (Short-Term Memory): последние N сообщений из Redis/DB для удержания нити диалога.Отправляет этот легкий пакет в AI-слой (Fast Loop).

## 2.3. DB Bridge (Транзакционный мост)

Управляет пулом соединений (`sqlx`) и атомарностью.

Бэкенд не выполняет вычисления (`balance = balance - 100`).

Бэкенд вызывает процедуры (`CALL rpc_create_transaction(...)`).

Если БД возвращает ошибку нарушения инварианта (например, ∑W=∑E), Бэкенд транслирует её в понятное пользователю сообщение.

## 2.4. Ephemeral Messenger Gateway

Модуль для обработки сообщений в реальном времени без сохранения истории переписки на сервере.

**Режим:** Active Session (активируется триггером `@sana`, или переходом в чат с ассистентом).

**Память:** Использует Redis для хранения "горячего контекста" с коротким TTL.

**Приватность:** Текст сообщения уничтожается из RAM сразу после извлечения финансового интента.

# 3. Система Спутников (Satellite Workers)

Тяжелые или рискованные задачи вынесены в изолированные бинарные процессы. Общение с Ядром идет через gRPC (Unix Sockets).

| Спутник | Роль и Функции | Источник |
| --- | --- | --- |
| sana-nostradamus | Predictive Engine. Моделирование сценариев будущего. Работает в Slow Loop, прогнозирует кассовые разрывы на основе recurring_patterns и obligations. |  |
| sana-crypto-sync | Blockchain Scanner. Stateless-воркер. Асинхронно опрашивает ноды, используя курсоры из blockchain_cursors. При падении перезапускается мгновенно. |  |
| sana-fx-engine | Currency Gateway. Кэширует курсы валют (Minute-Precision) в RAM. Обеспечивает данные для fx_rates_history с нулевой задержкой. |  |
| sana-report-worker | Document Generator. Генерирует тяжелые PDF/Excel выгрузки. Работает через очередь RabbitMQ. |  |
| sana-tax-worker | Compliance Engine. Выполняет сложные налоговые расчеты (режимы A, B, V), если логика выходит за рамки SQL-функций. |  |

# 4. Фабрика Адаптеров (External Adapters)

Слой абстракции (Rust Traits) для взаимодействия с внешним миром. Реализует принцип **Provider Agnostic**.

## 4.1. AI Factory (`ModelProvider`)

**Динамическое переключение:** Выбирает модель (Gemini Flash, Claude Opus, Groq) в зависимости от задачи и стоимости.

**Payload Delivery:** Передает провайдеру подготовленный контекст. Системные промпты (инструкции) инкапсулированы внутри конфигурации Агентов, а не формируются Бэкендом динамически.

## 4.2. Crypto Factory (`ChainInformer`)

**Агрегация:** Опрашивает несколько нод (Infura, Alchemy) и сверяет данные для защиты от скомпрометированных источников (Consensus Check).

## 4.3. Infrastructure Security

**Secret Injection:** API-ключи никогда не хранятся в коде. Они инжектируются в память процесса из **HashiCorp Vault** при старте контейнера.

# 5. Управление Данными и Состоянием

## 5.1. Real-Time State (Push Model)

Бэкенд держит WebSocket/gRPC-Web соединения с клиентами.

Как только транзакция закоммичена в БД (триггер обновил `user_snapshots`), Бэкенд **пушит** обновление (`safe_to_spend`, `net_worth`) в интерфейс, минуя опрос.

## 5.2. Pending Layer Management

Бэкенд управляет буфером неподтвержденных транзакций.

**Batching:** Группирует низкоприоритетные события (крипто-поступления) в дайджесты.

**Expiration:** Фоновый процесс очищает просроченные записи из `pending_layer` по TTL.


--------------------------------------------------------------------------------

# 6. Инфраструктурная Топология

Система работает в Kubernetes по принципу «Три кольца защиты»:

**Public Zone:** Load Balancer, WAF.

**Private Backend Zone:** Инстансы `sana-core` и спутников. Доступ извне закрыт.

**Private Data Zone:** PostgreSQL, Redis, RabbitMQ. Доступ только у `sana-core`.

**Надежность:**

**Panic Isolation:** Сбой в спутнике не роняет Ядро. Ядро перезапускает воркер.

**Result Pattern:** В коде Ядра запрещена паника (`panic!`), все ошибки обрабатываются явно.

# Резюме

Архитектура **Sana Backend** — это умный диспетчер. Он не перегружает ИИ лишней информацией, отдавая сначала только необходимый минимум (сообщение + краткая история). Данные подгружаются точечно, только если Дирижёр решит, что они нужны для ответа. Это обеспечивает максимальную скорость, экономию токенов и безопасность.
