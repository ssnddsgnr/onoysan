# 1. Философия: Исполнительное Ядро

Процесс `sana-core` — это высокопроизводительный асинхронный оркестратор. Все описанные ниже модули скомпилированы в единый бинарный файл для минимизации задержек (Zero-latency calls). **Ключевые архитектурные инварианты:**

**Identity Split:** Внутренние модули никогда не видят `telegram_id`, `nickname`, или `email`. Они оперируют только `internal_user_id`.

**No Math in Code:** Бэкенду запрещено выполнять финансовые вычисления (сложение, вычитание). Вся математика делегирована в SQL.

**Log Scrubbing:** Запрет на логирование сырых данных пользователя.

# 2. Модуль 1: Sanitary Gateway (Шлюз-Анонимайзер)

**Роль:** Пограничный контроль. Единственная точка входа для внешнего трафика (Telegram Webhook, REST API, gRPC).

## 2.1. Identity Injection (Инъекция Личности)

Шлюз перехватывает входящий запрос до того, как он попадет в бизнес-логику.

**Процесс:**Получает токен авторизации или payload от Telegram.Обращается к «горячему» кэшу авторизации (Redis) или таблице `auth.auth_identities`.Находит соответствие: `External ID (12345)` -> `Internal UUID (550e84...)`.**Подмена:** Создает новый объект контекста запроса, где `External ID` стерт, а `Internal UUID` внедрен как неизменяемое поле.

## 2.2. Log Scrubbing (Санитария Логов)

Реализует политику приватности на уровне системного вывода (stdout/stderr).

**Механизм:** Custom Formatter для трейсинга (tracing-subscriber).

**Фильтрация:** Применяет Regex-фильтры к телам сообщений перед записью в лог.*Вход:* "Перевод 5000 на карту 4400..."*Лог:* `[INFO] Intent: Transfer | Payload: [REDACTED size=24b]`

*Лог:* `[INFO] Intent: Transfer | Payload: [REDACTED size=24b]`

**Цель:** Исключить оседание PII (персональных данных) в системах мониторинга (Loki/Grafana).

## 2.3. Request Throttling

Защита от DDoS и спама на уровне токенов/пользователей (Rate Limiting), чтобы один активный чат не исчерпал лимиты API нейросетей.

# 3. Модуль 2: Cognitive Logistics (Когнитивная Логистика)

**Роль:** Управление потоком данных между Пользователем и AI-слоем. Реализует протокол «Context Integrity».

## 3.1. Raw Data Passthrough

Модуль передает сырые данные (OCR чека, транскрипцию голоса) в AI-слой (через Фабрику Адаптеров) **без искажений**.

**Зачем:** Любая попытка «зазвездить» данные (****) до анализа может разрушить контекст (например, AI не поймет, что "Магнит" — это магазин, а не физический объект). Безопасность обеспечивается тем, что эти данные живут только в оперативной памяти (RAM) и удаляются сразу после обработки.

## 3.2. Lazy Enrichment (Ленивое Обогащение)

Оптимизирует нагрузку на БД и потребление токенов LLM.

Сначала отправляет Дирижёру только сообщение пользователя и `Short-Term Memory` (последние N сообщений).

Если Дирижёр возвращает запрос `Require: [active_project_pnl]`, модуль делает точечный запрос в БД, получает P&L и повторяет вызов к ИИ с обогащенным контекстом.


--------------------------------------------------------------------------------

# 4. Модуль 3: Intent Validator (Валидатор Интентов)

**Роль:** Защита базы данных от стохастической природы (галлюцинаций) нейросетей. Последний рубеж обороны перед записью.

## 4.1. Schema Enforcement (Строгая Типизация)

AI возвращает JSON. Валидатор десериализует его в строгие Rust-структуры (`struct ProposedTransaction`).

**Проверки:**`amount` должен быть числом (не строкой "пятьсот").`currency` должна соответствовать ISO-коду или тикеру из справочника `system`.Если валидация не проходит — запрос отклоняется с ошибкой `422 Unprocessable Entity` (для ИИ это сигнал переформулировать интент), не нагружая БД.

## 4.2. Logic Check (Проверка Прав)

Предварительная проверка бизнес-логики (Pre-flight check).

Существует ли указанный `wallet_id`?

Принадлежит ли он текущему `internal_user_id` (или есть ли `access_grant`)?

*Примечание:* Это дублируется в БД (RLS), но проверка на бэкенде позволяет быстрее отдать ошибку и сэкономить ресурсы транзакции БД.


--------------------------------------------------------------------------------

# 5. Модуль 4: DB Bridge (Транзакционный Мост)

**Роль:** Управление персистентностью. Единственный модуль, имеющий право держать соединение с PostgreSQL.

## 5.1. Procedural Mapping (RPC Calls)

Вместо генерации SQL-запросов (ORM), этот модуль вызывает хранимые процедуры PL/pgSQL.

**Код:** `sqlx::query("CALL ledger.fn_create_transaction($1, $2...)")`

**Философия:** Бэкенд не знает, как считать налоги или балансировать леджер. Он просто передает команду "Создать транзакцию" и параметры. Вся ответственность за целостность данных лежит на процедуре БД.

## 5.2. Connection Pooling

Использует `sqlx::PgPool` для эффективного управления соединениями.

Поддерживает мультиплексирование запросов.

Автоматически переподключается при разрыве связи.

## 5.3. Result Mapping

Транслирует ошибки БД (Postgres Error Codes) в понятные для ИИ статусы.

Ошибка `P0001 (Raise Exception)` -> `Status::BusinessError("Недостаточно средств")`.

Ошибка `23505 (Unique Violation)` -> `Status::Conflict("Дубликат транзакции")`.

# 6. Вспомогательные Модули

## 6.1. Ephemeral Messenger Gateway

Специализированный модуль для обработки чатов.

**RAM-only:** Обрабатывает медиа-файлы (фото/голос) исключительно в памяти.

**Zero-Persistence:** Инициирует мгновенное удаление исходных данных (drop payload) после успешного извлечения интента.

## 6.2. Queue Dispatcher

Асинхронная разгрузка ядра.

Отправляет тяжелые задачи (например, генерацию PDF-отчета воркером `sana-report-worker`) в RabbitMQ. Использует паттерн "Fire-and-Forget" для неблокирующей работы основного потока.

# Резюме

Архитектура внутренних модулей `sana-core` построена на принципе **конвейера с фильтрами**.

**Gateway** очищает запрос от личности.

**Logistics** управляет общением с ИИ.

**Validator** проверяет адекватность ИИ.

**DB Bridge** исполняет волю пользователя руками базы данных. Это гарантирует, что даже если ИИ «сойдет с ума», он не сможет повредить финансовый реестр, так как упрется в жесткие проверки Валидатора и SQL-процедур.
