# 1. Философия: Активное Вычислительное Ядро

В архитектуре Sana база данных PostgreSQL выполняет роль **детерминированного вычислительного движка**. Мы сознательно переносим бизнес-логику (расчет налогов, балансировку леджера, проверку инвариантов) из кода бэкенда (Rust) в хранимые процедуры (PL/pgSQL).

## Принципы Слой Данных:

**Immutability (Неизменяемость):** Финансовая история — это линейный поток событий. Операции `DELETE` и `UPDATE` в таблицах транзакций физически запрещены триггерами. Ошибки исправляются только компенсирующими записями.

**Math in DB (Математика внутри):** ИИ и Бэкенд не производят финансовых расчетов. Они лишь запрашивают выполнение функций БД. Это исключает ошибки округления и «галлюцинации».

**Identity Split (Разрыв Личности):** Данные аутентификации (кто вы) и финансовые данные (сколько у вас денег) живут в изолированных доменах, связанных только анонимным UUID.

# 2. Топология Доменов Данных

Схема базы данных разделена на логические зоны ответственности для обеспечения безопасности и ясности структуры.

## Зона 1: Identity & Sovereignty (Идентификация и Доступ)

*Обеспечивает вход в систему и разграничение прав, не касаясь денег.*

**auth_identities**: Единственный шлюз. Хранит внешние ID (Telegram, Email) и мапит их на анонимный `internal_user_id`.

**users_metadata**: Хранит зашифрованные (Encryption at Rest) имена, настройки ИИ и локализацию. Никогда не джойнится с леджером в аналитических запросах.

**access_grants**: Реализация RBAC (Role-Based Access Control) для механики **Shared Sovereignty**. Определяет, кто имеет права `viewer` или `editor` к кошелькам и проектам.

## Зона 2: The Mirror Layers (Физика и Логика)

*Отражает реальность и смыслы. Здесь действует инвариант*∑Wallets≡∑Envelopes*.*

**wallets**** (Физический слой):** Иерархическая структура счетов (Parent/Child). Отражает реальные места хранения (Банки, Крипта, Наличные).

**envelopes**** (Логический слой):** Конверты смыслов. Цели, Обязательства, Налоги, Свободные траты. Имеют приоритеты для алгоритма распределения доходов (Waterfall).

**assets**** (Контекстный слой):** Имущество (Авто, Недвижимость). Служат «якорями» для привязки расходов (TCO) и прогнозов.

## Зона 3: The Immutable Core (Леджер)

*Центральный журнал событий. Единый источник истины.*

**ledger_transactions**: Главная таблица. Хранит атомарные события. Содержит ссылки на Wallet, Envelope, Project и (опционально) Asset. Поддерживает мультивалютность через фиксацию курса (`fx_rate_snapshot`) в момент записи.

**fx_rates_history**: Глобальный архив курсов валют с минутной точностью (Minute-Precision). Используется для исторической переоценки капитала.

## Зона 4: Business Logic (Проекты и Обязательства)

*Инструменты для P&L и управления будущим.*

**projects**: Контейнеры для бизнес-активности. Изолируют экономику конкретных заказов от личного бюджета.

**tax_rules**: Конфигурация **Tax Engine**. Определяет режимы (A, B, V) и ставки для авто-резервирования налогов.

**obligations**: Долги (Payable) и Ожидаемые поступления (Receivable). Основа для прогнозирования кассовых разрывов.

**project_balances**: Материализованные агрегаты P&L по каждому проекту (Доход - Расход - Налог).

## Зона 5: Cognitive Layer (ИИ и Интерфейс)

*Буферная зона для взаимодействия с пользователем и ИИ.*

**chat_sessions** и **chat_messages**: История контекста. Привязка диалогов к сущностям (Project/Goal).

**pending_layer**: «Зал ожидания» для черновиков транзакций, требующих **MVA** (подтверждения пользователем). Сюда пишет ИИ, но не пишет в Леджер.

## Зона 6: Performance & Analytics (Снапшоты)

*Ускоритель для чтения.*

**user_snapshots**: «Горячее» состояние. Одна строка на пользователя, содержащая агрегаты (Net Worth, Safe-to-Spend). Обновляется триггерами при любой записи в Леджер.

# 3. Логический Движок (PL/pgSQL Engine)

Вся критическая логика инкапсулирована в хранимые процедуры, образующие внутренний API базы данных.

## 3.1. Ядро Транзакций

**fn_create_transaction(jsonb)**: Главная точка входа.Проверяет права доступа и лимиты.Создает запись в `ledger_transactions`.Вызывает `Tax Engine` для расчета налогов.Обновляет балансы `wallets` и `envelopes`.Проверяет инвариант равновесия. Если ∑W=∑E — делает ROLLBACK.

Проверяет права доступа и лимиты.

Вызывает `Tax Engine` для расчета налогов.

Проверяет инвариант равновесия. Если ∑W=∑E — делает ROLLBACK.

**fn_reverse_transaction(tx_id)**: Создает сторнирующую запись, полностью нейтрализующую влияние ошибочной транзакции, сохраняя аудиторский след.

## 3.2. Tax Engine (Налоговый движок)

**fn_calculate_tax_reserve()**: Триггерная функция. При поступлении дохода проверяет `tax_rules` для кошелька/проекта. Если правило найдено, автоматически создает связанную транзакцию перевода части средств в конверт «Налоговый резерв» и помечает за что этот налог.

## 3.3. Snapshot Engine

**trg_update_user_snapshot**: Триггер AFTER INSERT на таблице транзакций. Мгновенно пересчитывает `safe_to_spend` и `net_worth` в таблице `user_snapshots`, обеспечивая ИИ свежими данными за <10ms.

# 4. Математические Инварианты

Система гарантирует целостность данных через ограничения (Constraints) и триггеры.

**Инвариант Равновесия:** В любой момент времени сумма средств на всех физических счетах пользователя должна быть равна сумме средств во всех логических конвертах. ∑Wallets≡∑Envelopes

**Инвариант Неизменяемости:** Попытка выполнить `DELETE` или `UPDATE` над `ledger_transactions` вызывает исключение на уровне БД.

**Инвариант Изоляции:** Благодаря RLS, запрос пользователя `A` технически не может вернуть строки пользователя `B`, даже если Бэкенд допустит ошибку в SQL.


--------------------------------------------------------------------------------

# 5. Прогностический слой (Hard Engine)

База данных содержит логику для детерминированного прогнозирования ликвидности.

**fn_forecast_liquidity(horizon_days)**: Строит временной ряд будущих балансов, вычитая из текущего остатка (`user_snapshots`) предстоящие события из `recurring_patterns` и `obligations`.

Если баланс уходит в минус — возвращает дату и сумму кассового разрыва для передачи в модуль **Nostradamus**.
