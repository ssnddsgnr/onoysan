# 1. Философия: Исполнительное Ядро

Процесс `sana-core` — это высокопроизводительный асинхронный оркестратор. Все модули скомпилированы в единый бинарный файл. **Ключевое изменение в безопасности:** Мы отказываемся от модификации входящего пейлоада (текста/фото) до обработки ИИ, чтобы сохранить контекст (гео-позицию, имена мерчантов). Приватность обеспечивается через **Identity Split** (отвязку данных от личности) и **Log Scrubbing** (запрет на логирование сырых данных).

# 2. Реестр Модулей (Module Registry)

## 2.1. Sanitary Gateway (Шлюз-Анонимайзер)

**Роль:** Пограничный контроль, нормализация трафика и анонимизация запросов.

**Identity Injection (Инъекция Личности):** Шлюз перехватывает входящие запросы. Он обращается к кэшу авторизации, извлекает `internal_user_id` и принудительно внедряет его в контекст.*Важно:* Внешние идентификаторы (Telegram ID, Email, IP) отсекаются на этом этапе. Вглубь системы и во внешние API (Google/Anthropic) уходит только анонимный UUID.

*Важно:* Внешние идентификаторы (Telegram ID, Email, IP) отсекаются на этом этапе. Вглубь системы и во внешние API (Google/Anthropic) уходит только анонимный UUID.

**Log Scrubbing (Санитария Логов):** Вместо очистки самого сообщения, модуль применяет Regex-фильтры к **системным логам**.*Логика:* Ядро «видит» текст «Перевод Ивану на Сбер», передает его в ИИ для анализа, но в `stdout`/`Loki` записывает: `[INFO] Processed Intent: Transfer | Payload: [REDACTED size=24b]`. Это гарантирует, что PII не оседают в логах серверов.

**Request Throttling:** Защита от DDoS и спама на уровне токенов.

## 2.2. Cognitive Logistics (Когнитивная Логистика)

**Роль:** Управление потоком данных между Пользователем и AI-слоем. Реализует протокол **«Context Integrity»**.

**Raw Data Passthrough:** Модуль передает сырые данные (OCR чека, транскрипцию голоса) в AI-слой без искажений. Это критично для того, чтобы Дирижёр мог понять контекст (например, по адресу ресторана определить категорию или по имени в голосовом сообщении — контакт из списка должников).

**Ingestion Strategy:** Обогащает запрос **«Краткосрочной памятью»** (Short-Term Memory) из Redis, чтобы ИИ понимал отсылки («добавь это к предыдущему проекту»).

**Lazy Enrichment:** Если Дирижёр запрашивает дополнительные данные (например, `Require: [active_project_pnl]`), модуль подгружает их из БД и повторяет вызов.

## 2.3. Intent Validator (Валидатор Интентов)

**Роль:** Защита базы данных от стохастической природы нейросетей.

**Schema Enforcement:** Строгая типизация JSON-интентов, полученных от AI. Если агент присылает строку там, где ожидается число, или галлюцинирует несуществующую валюту, Валидатор отклоняет запрос с ошибкой `422`, не нагружая базу данных.

**Logic Check:** Проверяет базовые условия: наличие прав доступа к указанному кошельку (`access_grants`) и существование конвертов.

## 2.4. DB Bridge (Транзакционный Мост)

**Роль:** Управление персистентностью через драйвер `sqlx`.

**Procedural Mapping:** Ядро вызывает хранимые процедуры PL/pgSQL (`CALL rpc_create_transaction(...)`). Вся математика выполняется внутри БД.

**Connection Pooling:** Эффективное управление соединениями для высокой пропускной способности.

## 2.5. Ephemeral Messenger Gateway (Эфемерный Шлюз)

**Роль:** Обработка чат-сессий в реальном времени с соблюдением **Zero-Persistence**.

**RAM-only Processing:** Медиа-файлы (фото чеков, аудио) и тексты сообщений обрабатываются исключительно в оперативной памяти.

**Lifecycle Policy:**Получение данных.Отправка в AI-слой (через `Sanitary Gateway`).Получение структурированного JSON-интента.**Мгновенное уничтожение** исходных данных (Raw Payload) из памяти (`drop(payload)`).*Результат:* На сервере никогда не хранятся архивы фото или голоса пользователей, только извлеченные финансовые факты в БД.

## 2.6. State Manager (Менеджер Состояния)

**Роль:** Обеспечение реактивности интерфейса (Push-модель).

**Snapshot Broadcasting:** Подписывается на канал уведомлений PostgreSQL (`LISTEN/NOTIFY`). Как только транзакция закоммичена, модуль пушит обновленный снапшот на клиентское устройство, минуя опрос.

## 2.7. Queue Dispatcher (Диспетчер Очередей)

**Роль:** Асинхронная разгрузка Ядра.

**Fire-and-Forget:** Отправляет ресурсоемкие задачи (генерация PDF, глубокий парсинг блокчейна) в шину сообщений (RabbitMQ). Основной поток `sana-core` никогда не блокируется.

# 3. Интеграция и Безопасность

**Panic Isolation:** Использование `Result<T, E>` повсеместно. Ошибки обрабатываются явно, не роняя процесс.

**Transit Security:** Все данные внутри кластера (между Core и Satellites) передаются по gRPC, а внешние вызовы к AI-провайдерам идут строго по HTTPS с использованием анонимных токенов сессии.

# Итог

Внутренние модули `sana-core` реализуют принцип **«Умный транзит»**. Мы не калечим данные регулярными выражениями на входе, позволяя ИИ работать с полным контекстом. Безопасность достигается тем, что мы:

Скрываем личность пользователя от AI (Identity Split).

Скрываем данные пользователя от наших логов (Log Scrubbing).

Не храним сырые данные дольше, чем нужно для обработки (Ephemerality).
