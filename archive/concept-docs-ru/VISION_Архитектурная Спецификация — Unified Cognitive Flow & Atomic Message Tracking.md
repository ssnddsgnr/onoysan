# VISION_Архитектурная Спецификация — Unified Cognitive Flow & Atomic Message Tracking

Этот документ фиксирует финальную логику когнитивного конвейера Sana. Мы внедряем архитектуру **«Унифицированного шлюза»**, где Дирижёр выступает центральным хабом, а агенты — интеллектуальными процессорами. Ключевое нововведение — **атомарность сообщения**, позволяющая группировать финансовые события на уровне одного акта коммуникации.


--------------------------------------------------------------------------------

**Статус:** Final Cognitive Architecture

**Роль:** Сквозная обработка интентов и управление речевой интерпретацией.

**Принцип:** «Один вход — один выход». Дирижёр управляет специалистами, а не потоками данных.


--------------------------------------------------------------------------------

# 1. Схема движения информации (The Cognitive Sandwich)

Система работает по строгому линейному пути, где данные проходят через фильтры сложности на каждом этапе.

## Путь Запроса (Ingestion):

Пользователь → Дирижёр (Вход) → Агент-Парсер (Vision/Audio/Text) → Backend (Unified Ingestion) → DB (PL/pgSQL)

## Путь Ответа (Egestion):

DB → Backend → Дирижёр (Выход) → Агент-Интерпретатор (Zen/Consigliere/Analyst) → Пользователь


--------------------------------------------------------------------------------

# 2. Слой извлечения: Автономная сложность

Каждый агент-парсер (Зрение, Голос, Текст) обладает максимальной компетенцией: он не просто «цифрует» данные, а **самостоятельно интерпретирует сложные запросы**.

**Мульти-интентность:** Если в одном фото чека или в одном голосовом сообщении («Запиши 1000 доход, из них 200 отложи на аренду и 50 на кофе») содержится несколько действий, парсер декомпозирует их сам.

**Унифицированный JSON:** Результат работы любого парсера — это стандартизированный объект, который отправляется в **единую точку входа Backend**. Бэкенду не важно, откуда пришли данные, он работает с универсальным форматом интентов.


--------------------------------------------------------------------------------

# 3. Атомарность сообщения: `message_id`

Для обеспечения максимальной прозрачности и возможности группировки мы вводим идентификатор **Message ID**.

**Группировка по событию:** Если одно сообщение породило три транзакции, все они помечаются одним `message_id` в Ledger.

**Зачем это нужно:** Это позволяет пользователю в UI (Web/App) увидеть не просто список транзакций, а сгруппированный блок: *«Результат вашего сообщения от 14:05»*. Это четвертый уровень вложенности после Проектов, Целей и Чатов.

**Контекстный мост:** Дирижёр использует этот ID, чтобы связать ответ системы с конкретным актом ввода, избегая путаницы при асинхронной обработке.


--------------------------------------------------------------------------------

# 4. Слой интерпретации: Дирижёр как Режиссёр

После того как Backend и БД подтвердили успешность или ошибку операций, Дирижёр берет на себя роль «Режиссера ответа».

**Анализ результата:** Дирижёр видит, что произошло (например, успешный доход + риск кассового разрыва).

**Назначение Голоса:**Если всё штатно → вызывает **Консильери**.Если есть аномалия или успех → вызывает **Аналитика**.Если ситуация требует поддержки или празднования → вызывает **Sana Zen**.

Если всё штатно → вызывает **Консильери**.

Если есть аномалия или успех → вызывает **Аналитика**.

Если ситуация требует поддержки или празднования → вызывает **Sana Zen**.

**Единый выход:** Независимо от выбранного «голоса», сообщение отправляется пользователю через **единый шлюз**, обеспечивая целостность диалога.


--------------------------------------------------------------------------------

# 5. Технические инварианты потока

**Инвариант единого входа:** Бэкенд имеет только один API-эндпоинт для приема когнитивных данных. Это упрощает аудит и защиту (WAF).

**Инвариант декомпозиции:** Дирижёр и Парсер совместно гарантируют, что сложное сообщение будет разбито на атомарные транзакции, прежде чем коснуться Ledger.

**Инвариант контекстной связности:** Каждое сообщение пользователя получает временный «слот» в памяти Дирижёра до тех пор, пока не будет сформирован и отправлен ответ.


--------------------------------------------------------------------------------

### Итог:

Эта архитектура делает Sana невероятно гибкой. Мы можем добавлять новые способы ввода (например, парсинг транзакций из VR или смарт-очков) или новые «голоса» интерпретации, не меняя структуру бэкенда. Система остается стройной: **Сложный интеллект внутри — простой и понятный диалог снаружи.**
