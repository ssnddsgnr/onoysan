# VISION_Архитектурная Спецификация — PL/pgSQL Database Logic Engine

Этот документ определяет роль и структуру серверного программирования внутри базы данных. В архитектуре Sana **PostgreSQL** — это не просто хранилище, а **активный вычислительный движок**. Мы переносим критическую финансовую логику в PL/pgSQL, чтобы гарантировать целостность данных на самом низком уровне.


--------------------------------------------------------------------------------

**Статус:** Engineering Specification

**Роль:** Обеспечение атомарности, соблюдение математических инвариантов и инкапсуляция бизнес-логики.

**Принцип:** «Data and Logic live together».


--------------------------------------------------------------------------------

# 1. Философия: База данных как Гарант Истины

В отличие от традиционных систем, где логика размазана по Backend-сервисам, в Sana **все расчеты Ledger происходят внутри БД**.

**Атомарность:** Транзакция либо полностью соответствует правилам системы (налоги вычтены, баланс сошелся), либо она отклоняется базой.

**Производительность:** Мы избегаем лишних пересылок данных между БД и Rust-бэкендом для промежуточных вычислений.

**Безопасность:** Доступ к таблицам ограничен; взаимодействие происходит только через строго определенные интерфейсы функций.


--------------------------------------------------------------------------------

# 2. Основные функциональные модули (Namespace)

Функции группируются по зонам ответственности. Каждая группа имеет возможность расширения через добавление новых процедур.

## Группа А: Core Ledger (Ядро реестра)

Отвечает за базовое движение средств и соблюдение уравнения равновесия:

∑Wallets=∑Envelopes

**fn_create_transaction**: Принимает сырые данные об операции, проверяет лимиты и одновременно обновляет баланс кошелька и соответствующего конверта.

**fn_reverse_transaction**: Механизм «Права на ошибку». Создает корректирующую запись, сохраняя аудит.

**fn_reality_sync**: Выполняет балансировку между физическим и логическим слоями при обнаружении расхождений.

## Группа Б: Tax Engine (Налоговый модуль)

Автоматизирует вычисления в момент срабатывания триггера транзакции.

**fn_calculate_tax_reserve**: Рассчитывает сумму налога на основе `tax_rules` проекта или кошелька.

**fn_apply_tax_deduction**: Пересчитывает налоговую базу при регистрации вычитаемых расходов (Режим Б).

## Группа В: Project & P&L Intelligence

Синтезирует аналитические данные из потока транзакций.

**fn_get_project_pnl**: Динамически собирает отчет о доходах и расходах для конкретного `project_id`, учитывая авансы и налоги.

**fn_calculate_burn_rate**: Прогнозирует дату исчерпания бюджета проекта на основе истории.

## Группа Г: Access & Shared Sovereignty

Управляет правами доступа на уровне строк (Row-Level Security).

**fn_check_access_right**: Проверяет, имеет ли текущий `user_id` право видеть или изменять сущность (конверт/счет).

**fn_delegate_access**: Регистрирует новые связи в системе разделяемого суверенитета.

# 3. Спецификация расширяемости (Extensibility Pattern)

Архитектура функций Sana построена по принципу **«Hook-and-Service»**, что позволяет добавлять новые финансовые инструменты без переписывания ядра.

**Стандартизация входа/выхода:** Все функции обмениваются данными через строго типизированные JSONB-объекты или кастомные типы (Composite Types).

**Триггерная система:** Каждая транзакция вызывает цепочку автоматических проверок (проверка на отмывание, налоги, достижение целей).

**Добавление новых сущностей:** Чтобы добавить, например, «Кредитное плечо» или «Инвестиционный портфель», достаточно:Создать новую функцию в соответствующем пространстве.Зарегистрировать её в основном диспетчере транзакций `fn_create_transaction`.

# 4. Обработка ошибок и Инварианты

Каждая функция PL/pgSQL в Sana содержит блок `EXCEPTION`, который гарантирует, что система никогда не уйдет в неопределенное состояние.

**Математический Check:** Перед завершением функции проверяется, что итоговый баланс не стал отрицательным (если это запрещено правилами конверта).

**Logging:** Любая ошибка функции записывается в системный лог с полным контекстом входящих данных для последующего анализа Дирижёром.


--------------------------------------------------------------------------------

# 5. Итог для разработки

PL/pgSQL слой — это **фундаментальный закон** Sana. Backend на Rust выступает лишь в роли оркестратора, который вызывает эти функции. Это делает систему невероятно устойчивой: даже если Backend будет полностью переписан на другом языке, финансовая логика внутри БД останется нетронутой и верной.
