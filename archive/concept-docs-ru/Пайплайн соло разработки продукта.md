# Философия и основные принципы

## Базовые убеждения

**Документация живёт дольше кода** -- архиектурные решения компаундятся годами.

**Statless AI** требует явного контекста -- каждая сессия должна быть самодостаточной.

**Ограничения ускоряют исполнение** -- ограниченный набор инструментов заставляет мыслить чётко.

**Сначала архитектура, потом имплементация** -- думай глубоко один раз, пиши код быстро после.

## Инвариантные правила (лучше не нарушать)

**Правило 1:** Каждое архитектурное решение должно быть задокументированно перед имплементацией.

**Правило 2:** AI инструменты -- интерпритаторы, не лица принимающия.

**Правило 3:** Единственный источник правды существует (Notebook LM и Obsidian), все остальные источники -- кэши.

**Правило 4:** Версионный контроль для документации и кода (Git).

**Правило 5:** Никакой имплементации фичи без отсутствующего документа `SPEC`.

# Экосистема инструментов

## Основные инструменты и зоны ответсвенности

### Матрица ответственности инструментов:

| Инструмент: | Основная ответсвенность: |
| --- | --- |
| Obsidian | Ежедневное планирование, декомпозиция задач, персональный Knowledge manegement. |
| Gemini | Интерпритация архитектуры, создание черновиков документов из грубых идей. |
| NoteBook LM | Единственный источник правды, вся финализированная документация, база знаний проекта. |
| Claude (projects) | Имплиментация кода, решение технических проблем, валидация архитектуры. |
| GitHub | Версонный контроль для docs + code, интерфейс коллоборации. |

## Критерии выбора инструмента

### Когда использовать obsidian:

Ежедневное планирование задач и ретроспективы.

Персональная заметка и документация обучения.

Быстрая фиксация идеи (**inbox**-система).

Трекинг времени и метрик продуктивности.

### Когда использовать Gemini:

Конвертация грубых архитектурных мыслей в структурированные документы.

Расширение высокоуровневых концепций в детальные спецификации.

Запросы к NoteBook LM базе знаний для получения контекста.

Мозговой штурм альтернативных подходов.

### Когда использовать Notebook LM:

Хранение всей финализированной, верифицированной документации.

Запросы к знаниям проекта.

Генеральное саммари проекта.

Подготовка контекста перед сессиями с Claude.

### Когда использовать Claude:

Написание production кода.

Отладка сложных технических проблем.

Code Review и оптимизация.

Валидация архитектуры (соответствует ли `SPEC` реальности?)

### Когда использовать Git:

Каждое изменение в `/docs/` дирректории.

Каждый коммит кода в `/backend/`, `/migrations/`

Создание снапшотов перед крупными рефакторингами.

Трекинг "as-implemented" состояния.

# Иерархия документов

### Система уровней

```
TIER 0: Философия (Постоянные, Редко Меняются) 
└─ README.md // Миссия проекта, elevator pitch 
└─ stack.md // Выбор технологий 
└─ invariants.md // Неизменяемые правила

TIER 1: Стратегический (Blueprint Уровень) 
└─ BLUEPRINT.md // Мастер-документ архитектуры

TIER 2: Тактический (Vision Уровень) 
└─ vision-*.md // Основные слои системы (7-10 документов)

TIER 3: Операционный (Architecture Уровень) 
└─ arch-*.md // Дизайн подсистем (20-30 документов)

TIER 4: Имплементация (Specification Уровень) 
└─ spec-*.md // Детальные технические спеки (100+ документов)

TIER 5: Решения (Живая Запись) 
└─ decisions.md // Хронологический лог решений

TIER 6: Эфемерный (Специфичные для Сессии) 
└─ session-summary-YYYYMMDD.md // Заметки после сессии
```

### Матрица хранения

| Тип документа | Obsidian | Notebook LM | Claude | Git |
| --- | --- | --- | --- | --- |
| Tier 0 (философия) | Draft -> Final | Final | Always | Да |
| Tier 1 (Blueprint) | Draft -> Final | Final | Always | Да |
| Tier 2 (Vision) | Draft -> Final | Final | Rotate | Да |
| Tier 3 (Architecture) | Draft -> Final | Final | On-Demand | Да |
| Tier 4 (Specifications) | Нет | Final | Chat-only | Да |
| Tier 5 (Decissons) | Нет | Final | Always | Да |
| Tier 6 (Эфермерный) | Да | Нет | Нет | Нет |

### Легента:

`final` & `always` = Основное хранилище `Draft` = Только work-in-progress `Rotate` = Загружать/выгружать в зависимости от текущей задачи `On-demand` = Copy-paste в чат по требованию `Chat-only` = Никогда не хранится в файлах проекта

# Рабочий процесс разработки

## Фаза 1: Идеация -> Документация

### Шаг 1: Фиксация глубокой идеи (Obsidian + Gemini)

Длительность: 15-30 минут Результат: заметка в Obsidian Inbox **Шаблон:**

```
# Идея [Название]
## Проблема 
[Какую боль решаем?]
## Предлагаемое решение 
[Высокоуровневый поддход]
## Открытые вопросы
[- Вопрос 1]
[- Вопрос 2]
```

### Шаг 2: Расширение через Gemini (с контектсом Notebook LM)

Длительность: 30-60 минут Процесс:

Загрузить заметку в Gemini;

Предоставить контекст Notebook LM (существующая архитектура);

Запрос: "Разверни это в формат [SPEC/ARCH/VISION]";

Интерировать пока черновик не будет готов на 80%;

Результат: структурированный документ (черновой);

### Шаг 3: Верификация и финализация (ручной обзор)

Длительность: 15-30 минут

Чеклист:

[ ] Соответсвтует invariants.md

[ ] Нет противоречий с существующими `VISION`-документами

[ ] Реализуемо с текущим `stack.md`

[ ] Чёткие критерии приёмки определены

Действие: Ручной обзор, правки, утверждение.

### Шаг 4: Публикация в Notebook LM + Git

Длительность: 5 минут

Действия:

Загрузить в Notebook LM (становится источником правды);

Сохранить в `/docs/[tier]/` в локальном репозитории;

Git коммит: `"docs: add [name] specification"`;

Push в GitHub.

Результат: Документ теперь официальный, готов к имплементации.

## Фаза 2: Имплементация

### Шаг 5: Подготовка контекста Claude

Длительность: 5 минут

Действия:

Определить релевантные Tier 0-2 документ для задачи;

Добавить удалить из папки проекта Claude;

Взять Tier 4 (`SPEC`) из Notebook LM если нужно;

Проект Claude должен всегда содержать:

`stack.md` -- всегда;

`invariants.md` -- всегда;

`decisions.md` -- всегда (не забывать обновлять);

`blueprint.md` -- всегда;

`1-2 VISION.md` -- релевантные текущей задаче;

`/backend/code` -- авто-синхронизирован;

`SPEC.md` -- вставлять только прямо в чат.

### Шаг 6: Начало сессии Claude с блоком контента

**Шаблон первого сообщения:**

```
Контекст: "Задача [конкретная цель], область [работаем над: [слой/подсистема]], имплементируем: [фича/фикс/рефакторинг]"
```

**Загруженные документы:**

Tier 0: stack.md, invariants.md;

Tier 1: BLUEPRINT.md;

Tier 2: vision-[X].md;

SPEC -- вставленны прямо в чат.

**Ограничения:**

Любые специфичные для сессии ограничения.

### Шаг 7: Цикл имплементации (Claude-чат)

Длительность: 2-4 часа за сессию

Паттерн:

```
Я: "Имплементируй [конкретный компонент]"
Claude: "[генерирует код следуя инвариантам]"
Я: Обзор, тестирование, итерация
Claude: Уточнение на основе фидбека
---
Проверки в середине сессии: Каждые 30 минут: подтверди, что следуем invcariants.md 
---
Если застрял >15 минут: "Объясни trade-offs подхода A/B"
---
Красные флаги для остановки сессии: Claude предлагает нарушить инварианты; сгенерированный код противоречит стеку; требуется архитектурное решение (-> сначала создать ADR) 
```

### Шаг 8: Завершение сессии

Длительность: 15 минут

Действия:

Протестировать код; локально (компиляция, запуск, базовая валидация);

Git-коммит:  "[feat: что было построено]";

Обновить decisions.md если было архитектурное решение;

Создать summary сессии в obsidian.

**Шаблон заметки в Obsidian:**

```
# Сессия: YYYY-MM-DD
# [Название задачи]
| Начало | Конец | Статус |
# Что сделанно:
# Решения: [Решения с обоснованием] если есть -- обновить decision.md
# Блокеры: [описание проблемы + следующие шаги]
# Следующая сессия [Главная приоритетная задача]
```

## Фаза 3: Валидация и итерация

### Шаг 9: Reality Check (As-Built vs Spec)

Частота: после завершения каждой крупной фичи

Длительность: 30 минут

Процесс:

Сравнить сравнить имплементированный код с оригинальным `SPEC`;

Задокументировать отклонения (они всегда будут);

Решить: обновить `SPEC` или рефакторить код. Пути обновления: A. Минорное отклонение -> Заметка в decisions.md B. Крупное отклонение -> Обновить `SPEC`, коммит как V2
C. SPEC был неправ -> Создать `ADR` объясняющий почему

### Шаг 10: Синхронизация с Notebook LM

Цель: Поддерживать единственный источник правды актуальным

Действия:

Экспортировать все `/docs/` из Git;

Загрузить в Notebook LM (обновить источники);

Проверить отсутствие противоречивой информации;

Сгенерировать саммари для стейкхолдеров

## Шаблон 2: invariants.md (Tier 0)

```
# Инварианты Проекта 
**Проект**: [Название Проекта] 
**Последнее Обновление**: [YYYY-MM-DD] 
Эти правила НИКОГДА не меняются без явного Architecture Decision Record (ADR). 

--- 
## Целостность Данных 
### INV-001: Финансовая Точность 
**Правило**: Все денежные значения хранятся как `BIGINT` (minor currency units) 
**Обоснование**: Избежать ошибок округления с плавающей точкой 
**Пример**: - ✅ 150050 (тыйын) = 1500.50 KGS - ❌ 1500.50 (DECIMAL) — запрещено 
**Штраф за Нарушение**: Повреждение данных, бухгалтерские расхождения 

--- 
### INV-002: Неизменяемый Audit Trail 
**Правило**: Критичные действия (изменения статуса, правки цен) логируются в таблицу `audit_logs` 
**Обоснование**: Детекция фрода, разрешение споров 
**Имплементация**: PostgreSQL триггеры (нельзя обойти в application code) 
**Штраф за Нарушение**: Потеря доверия бизнеса, юридическая ответственность 

--- 
### INV-003: Только Soft Delete (После MVP) 
**Правило**: Никаких команд `DELETE` на production таблицах после MVP 
**Обоснование**: Восстановление данных, сохранение audit trail 
**Имплементация**: Колонка `deleted_at TIMESTAMPTZ` + фильтры в запросах 
**Исключение**: Очистка тестовых данных в development окружении 

--- 
## Безопасность 
### INV-004: Изоляция Тенантов 
**Правило**: Каждый запрос включает фильтр `shop_id` (shop UUID) 
**Обоснование**: Безопасность multi-tenant SaaS 
**Имплементация**: Применяется на уровне приложения (Rust middleware) 
**Штраф за Нарушение**: Утечка данных между клиентами (катастрофично) 

--- 
### INV-005: Аутентификация через Telegram ID 
**Правило**: Никаких паролей, никакого OAuth — только `telegram_id` (BIGINT) 
**Обоснование**: Простота UX, безопасность через инфраструктуру Telegram 
**Имплементация**: Идентичность пользователя = Telegram user ID 
**Исключение**: Будущие enterprise клиенты могут требовать SSO (отдельный auth сервис) 

--- 
## Дизайн API 
### INV-006: AI Никогда Не Трогает БД Напрямую 
**Правило**: LLM выдаёт JSON → Rust валидирует → Rust выполняет SQL 
**Обоснование**: Предотвратить повреждение данных от галлюцинаций 
**Имплементация**: Structured outputs + валидация схемы в Rust 
**Штраф за Нарушение**: Повреждение данных, непредсказуемое поведение 

--- ### INV-007: Порог Уверенности для Авто-Исполнения 
**Правило**: Действия исполняются только если LLM `confidence_score > 0.85` 
**Обоснование**: Предотвратить ущерб от недопонимания 
**Имплементация**: JSON схема требует поле `confidence` 
**Исключение**: Owner может переопределить в ручном режиме 
--- 
## Производительность 
### INV-008: Stateless Backend 
**Правило**: Никакого in-memory session state (кроме Redis кэша для производительности) 
**Обоснование**: Горизонтальное масштабирование, устойчивость к крашам 
**Имплементация**: Каждый запрос несёт полный контекст (JWT или session token) 

--- 
### INV-009: Запросы к БД Под 100ms (P95) 
**Правило**: 95-й перцентиль latency запросов < 100ms 
**Обоснование**: Требование real-time чат UX 
**Имплементация**: Правильные индексы, connection pooling, оптимизация запросов 
**Измерение**: Prometheus метрики, алерт при нарушении 

--- 
## Организационные 
### INV-010: Документация Перед Имплементацией 
**Правило**: Никакой фичи в коде без соответствующего Spec документа 
**Обоснование**: Ясность архитектуры, будущая поддерживаемость 
**Имплементация**: Pull request отклонён если отсутствует `/docs/specs/[feature].md` 
**Исключение**: Hotfixes менее 10 строк кода

## Шаблон 3: decisions.md (Tier 5)

**Формат:** Хронологический (новейшие первыми)

```
# Лог архитектурных решений проекта
---
### YYYY-MM-DD: [Краткое название решения]
Контекст: [Какую проблему решали?]
Решение: [Какое решение выбрали?]
Обоснование: [Почему это вместо альтернатив?]:
- Опция A: [почему отклонена?]
- Опция B: [почему отклонена?]
Последствия: 
- Плюсы: [преимущества]
- Минусы: [компромиссы]
Треггер пересмотра: [Что должно произойти чтобы пересмотреть?]
---
[ниже живой пример]
### 2024-05-12: Использование BIGINT для Денег Вместо DECIMAL
**Контекст**: Нужно хранить цены и суммы без ошибок округления **Решение**: Хранить все денежные значения как BIGINT (minor currency units: тыйын, копейки) **Обоснование**:
- DECIMAL/FLOAT имеют проблемы точности (0.1 + 0.2 ≠ 0.3 в IEEE 754)
- Целочисленная арифметика точна и быстрее
- Индустриальный стандарт (Stripe, Square используют этот подход) **Рассмотренные Альтернативы**:
- DECIMAL(10,2): Отклонено из-за возможного округления в вычислениях
- Хранить как строки: Отклонено (нельзя делать арифметику в SQL) **Последствия**:
- ✅ Плюсы: Идеальная точность, никаких финансовых расхождений
- ❌ Минусы: Менее читаемо в сырых SQL запросах (150000 vs 1500.00) **Триггер Пересмотра**: Если расширимся на криптовалюты (они используют 8+ десятичных знаков)
```
