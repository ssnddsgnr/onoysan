Этот документ описывает ресурсы, находящиеся в зоне **Private Data Zone** и **Private Backend Zone**. Доступ к этим ресурсам строго регламентирован: они не имеют публичных интерфейсов, а управление их состоянием осуществляется исключительно через процесс **sana-core** (Rust Master Process).

**Статус:** Engineering Specification / Security Protocol **Принцип доступа:** Exclusive Owner / Connection Pooling **Сетевая топология:** Private Data Zone (No Internet Access)


--------------------------------------------------------------------------------

# 1. Персистентное хранилище (The Vault)

**Ресурс:** PostgreSQL 16+ (Primary + Read Replicas) **Роль:** Единый источник истины (SSoT) и вычислительный движок бизнес-логики.

Ядро системы (`sana-core`) является **монопольным владельцем** пула соединений на запись. Прямой доступ к таблицам для других сервисов (кроме Admin-панели Appsmith через VPN) физически закрыт.

**Протокол:** Native PostgreSQL Protocol (via `sqlx` / `deadpool`).

**Управление соединениями:****Write Pool:** Эксклюзивно у `sana-core`. Гарантирует сериализуемость транзакций.**Read Pool:** Доступен для `sana-nostradamus` (аналитика) и `sana-report-worker` (генерация отчетов) с правами `RO`.

**Write Pool:** Эксклюзивно у `sana-core`. Гарантирует сериализуемость транзакций.

**Read Pool:** Доступен для `sana-nostradamus` (аналитика) и `sana-report-worker` (генерация отчетов) с правами `RO`.

**Инвариант изоляции логики:** Вся финансовая математика инкапсулирована в PL/pgSQL процедурах (`fn_create_transaction`, `fn_calculate_tax_reserve`). Ядро вызывает функции, но не дублирует логику расчетов в коде приложения,.

**Безопасность:** Row-Level Security (RLS) активировано принудительно для всех соединений.

# 2. Эфемерное состояние (The Cache)

**Ресурс:** Redis (Cluster Mode) **Роль:** Оперативная память для «горячих» данных, сессий и координации блокировок.

Используется для данных, потеря которых не критична для финансового баланса (Ledger), но критична для UX (скорость ответа).

**Данные:****Minute-Precision FX:** Актуальные курсы валют, обновляемые `sana-fx-engine`.**User Sessions:** Токены авторизации и контекст чатов (TTL < 24h).**Distributed Locks:** Механизм координации для предотвращения Race Conditions при обработке очередей.

**Minute-Precision FX:** Актуальные курсы валют, обновляемые `sana-fx-engine`.

**User Sessions:** Токены авторизации и контекст чатов (TTL < 24h).

**Distributed Locks:** Механизм координации для предотвращения Race Conditions при обработке очередей.

**Инвариант чистоты:** **Строжайше запрещено** хранить в Redis данные Ledger или транзакций. Redis считается ненадежным хранилищем (Volatile Storage).

# 3. Асинхронная шина (The Nervous System)

**Ресурс:** RabbitMQ (или NATS JetStream) **Роль:** Декаплинг (развязывание) процессов приема данных и их обработки. Гарантирует, что пиковые нагрузки не «уложат» Ядро.

**Очереди (Queues):**`ingestion_events`: Входящие вебхуки от Telegram/Frontend.`blockchain_events`: Транзакции, найденные сканерами `sana-crypto-sync`.`media_processing`: Ссылки на фото/аудио для парсинга.

`ingestion_events`: Входящие вебхуки от Telegram/Frontend.

`blockchain_events`: Транзакции, найденные сканерами `sana-crypto-sync`.

`media_processing`: Ссылки на фото/аудио для парсинга.

**Dead Letter Queue (DLQ):** Изолятор для событий, вызвавших панику воркеров или не прошедших валидацию схем. Это предотвращает бесконечные циклы перезапуска задач.

**Управление:** `sana-core` выступает в роли продюсера и консьюмера, управляя подтверждением обработки (ACK/NACK).

# 4. Транзитное медиа-хранилище (The Buffer)

**Ресурс:** Object Storage (S3-compatible / MinIO) **Роль:** Временный буфер для неструктурированных данных (фото чеков, аудиосообщения, сгенерированные PDF-отчеты).

**Политика жизненного цикла (Lifecycle Policy):****Входящие (Input):** Фото и аудио удаляются немедленно после успешного извлечения интентов (OCR/Transcription).**Исходящие (Output):** Сгенерированные PDF-отчеты хранятся с TTL 24 часа, после чего физически уничтожаются.

**Входящие (Input):** Фото и аудио удаляются немедленно после успешного извлечения интентов (OCR/Transcription).

**Исходящие (Output):** Сгенерированные PDF-отчеты хранятся с TTL 24 часа, после чего физически уничтожаются.

**Безопасность:** Server-Side Encryption (SSE) включено по умолчанию. Доступ к объектам только через временные подписанные URL (Presigned URLs), генерируемые Ядром.

# 5. Управление секретами (The Keyring)

**Ресурс:** HashiCorp Vault / K8s Secrets **Роль:** Хранение ключей шифрования и доступов к внешним API.

Ядро следует принципу **«Secretless Code»**. В исходном коде и Docker-образах отсутствуют какие-либо чувствительные данные.

**Механизм:** Секреты инжектируются в процесс `sana-core` только в момент запуска (Runtime Injection) через переменные окружения или монтируемые тома в памяти.

**Состав:**Ключи шифрования БД (`users_metadata`).API Keys внешних адаптеров (Gemini, Claude, Etherscan).Соль для хэширования Identity Hash.

# 6. Управляемые Спутники (Satellite Binaries)

**Ресурс:** Изолированные процессы-воркеры **Роль:** Специализированные вычисления, вынесенные за пределы основного процесса для защиты памяти и CPU Ядра.

`sana-core` выступает для них в роли **Process Manager** (аналог Supervisor). Взаимодействие происходит через gRPC over Unix Domain Sockets (для локальных спутников) или TCP (для разнесенных).

**Список управляемых ресурсов:**`sana-nostradamus`: Тяжелые AI-вычисления и прогнозирование (Slow Loop).`sana-crypto-sync`: Stateless-сканер блокчейнов.`sana-tax-worker`: Расчет сложных налоговых схем.

`sana-nostradamus`: Тяжелые AI-вычисления и прогнозирование (Slow Loop).

`sana-crypto-sync`: Stateless-сканер блокчейнов.

`sana-tax-worker`: Расчет сложных налоговых схем.

**Политика изоляции:** Спутники имеют жесткие лимиты ресурсов (CPU/RAM Quotas) в K8s. Падение спутника (OOM Kill) не приводит к падению Ядра — Core просто перезапускает процесс.

# Резюме архитектора

В этой топологии **sana-core** (Rust) является единственным субъектом, обладающим полнотой власти над инфраструктурой.

Никто, кроме Core, не пишет в **PostgreSQL**.

Никто, кроме Core, не читает из **RabbitMQ** (в контексте бизнес-логики).

Никто, кроме Core, не управляет жизненным циклом секретов.

Это обеспечивает **Детерминизм**: состояние системы меняется только через предсказуемые, валидируемые и аудируемые действия центрального оркестратора.
