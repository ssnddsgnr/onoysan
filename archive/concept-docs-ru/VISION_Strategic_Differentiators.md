# 1. Фундаментальное позиционирование

Рынок PFM (Personal Finance Management) традиционно предлагает инструменты для *наблюдения* за прошлым (Reporting). Sana позиционируется как операционная система для *управления* текущим состоянием и моделирования будущего (Execution & Forecasting). **Ключевое отличие:**

**Трекеры:** Реализуют парадигму «Зеркало заднего вида». Пользователь видит факт списания постфактум.

**Sana:** Реализует парадигму «GPS-навигации». Система рассчитывает маршрут (кассовые разрывы, достижение целей) в момент каждой транзакции.

# 2. Архитектурные отличия (Backend & Data)

## 2.1. Event-Sourcing вместо CRUD

Большинство финансовых приложений используют архитектуру CRUD (Create, Read, Update, Delete), где изменение баланса перезаписывает предыдущее состояние.

### Подход Sana:

Используется **Event-Driven Architecture**. Каждое действие (расход, приход, корректировка) — это неизменяемое событие (Event), которое дописывается в журнал (Log).

### Техническое следствие:

**Аудируемость:** Полная история изменений доступна всегда. Удаление технически невозможно (только сторнирование).

**Восстановление:** Состояние системы можно восстановить на любую миллисекунду в прошлом.

## 2.2. Детерминированные вычисления (Logic in DB)

Конкуренты часто переносят логику расчетов на бэкенд приложения или доверяют ее ИИ.

### Подход Sana:

Вся финансовая математика инкапсулирована в **PostgreSQL (PL/pgSQL)**.

### Техническое следствие:

Исключены ошибки округления на уровне приложения и «галлюцинации» нейросетей. ИИ используется только для интерфейса, математика остается строго детерминированной.

## 2.3. Snapshot Model (Мгновенный доступ)

Вместо пересчета истории транзакций при каждом запросе (Full Scan), Sana использует архитектуру предрасчитанных состояний.

### Механизм:

Триггеры DB обновляют таблицу `user_snapshots` при каждой записи в реестр.

### Результат:

Ответ на вопрос «Сколько денег?» занимает <100ms независимо от глубины истории.

# 3. Отличия в модели данных

## 3.1. Многослойная реальность (Multi-Layer Reality)

Обычные трекеры оперируют плоским списком счетов. Sana разделяет данные на три связанных слоя:

**Физический (Wallets):** Реальные остатки (Банки, Крипта, Наличные).

**Логический (Envelopes/Obligations):** Распределение средств по целям и долгам.

**Контекстный (Projects/Assets):** Привязка трат к бизнес-проектам и имуществу. **Инвариант:** ∑Wallets≡∑Envelopes.

## 3.2. Гибридная модель ввода (Manual Fiat + Auto Crypto)

Sana объединяет полярные подходы к вводу данных:

**Фиат:** Только ручной ввод или парсинг чеков/сообщений (MVA). Причина: безопасность (Air-Gap) и осознанность трат.

**Криптовалюта:** Полная автоматизация через Read-Only сканеры блокчейна (`sana-crypto-sync`). Причина: высокая сложность ручного учета газа и транзакций.

# 4. Отличия в стратегии взаимодействия (AI-Native)

## 4.1. Диалог вместо транзакции

Интерфейс не является набором форм. Это чат, где ИИ управляет контекстом.

**Cognitive OS:** Система помнит контекст предыдущих сообщений («Сколько я потратил *на это*?» — система понимает, что «это» относится к обсуждаемому проекту).

**Бесшовность:** Пользователь не выбирает категории из списка вручную. ИИ-парсер извлекает мерчанта, категорию и проект из естественного языка или фото.

## 4.2. Предиктивная суверенность (Nostradamus)

Вместо статичных бюджетов («Лимит $500») система использует динамическое прогнозирование.

**Функция:** SQL-движок проецирует текущие регулярные траты и обязательства на временную шкалу.

**Результат:** Выявление кассовых разрывов (отрицательного баланса) в будущем. Система предупреждает о проблеме до ее возникновения.

# 5. Безопасность и Приватность

## 5.1. Air-Gap (Отсутствие банковских интеграций)

Sana принципиально не использует агрегаторы банковских API (Plaid, SaltEdge) для фиатных счетов.

**Безопасность:** Банковские учетные данные никогда не покидают пользователя.

**Независимость:** Работоспособность системы не зависит от сбоев банковских API или санкционных ограничений.

## 5.2. Identity Split

Архитектурное разделение личности и финансов. **Реализация:** Финансовое ядро (Ledger) оперирует только анонимным `internal_user_id`. Связка с Telegram/Email/Google/Apple ID находится в изолированной базе Auth. Даже при утечке дампа Ledger невозможно установить владельцев кошельков.

# Резюме

Sana — это «Когнитивная Финансовая ОС», потому что она:

**Управляет состоянием** через детерминированное ядро (PostgreSQL).

**Обеспечивает интерфейс** через ИИ-слой (Natural Language).

**Гарантирует безопасность** через архитектуру Air-Gap и Event-Sourcing. В отличие от трекера, который отвечает на вопрос «Сколько денег потрачено?», Sana отвечает на вопрос «Как ими распорядиться сейчас, чтобы не было проблем потом?».
