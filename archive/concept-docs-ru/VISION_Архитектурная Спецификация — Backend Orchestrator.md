# VISION_Архитектурная Спецификация — Backend Orchestrator

Этот документ завершает техническое описание «двигателя» Sana. Если PostgreSQL — это закон и память, то **Backend на Rust** — это центральная нервная система и главный исполнитель. Он связывает хаос пользовательского ввода с жесткой дисциплиной базы данных.


--------------------------------------------------------------------------------

**Статус:** Final Engineering Specification

**Роль:** Оркестрация, высокоуровневая валидация и мост между ИИ и Ledger.

**Принцип:** «Stateless & Fearless». Бэкенд не хранит состояние, он управляет потоком.


--------------------------------------------------------------------------------

# 1. Технологический выбор: Почему Rust?

В 2026 году для финансового ядра не существует альтернатив Rust, обеспечивающих такой же уровень безопасности и производительности.

**Memory Safety (Безопасность памяти):** Исключение целого класса ошибок (Null pointers, Buffer overflows), которые в других языках приводят к критическим уязвимостям.

**Zero-Cost Abstractions:** Максимальная скорость обработки транзакций при минимальном потреблении ресурсов (важно для K8s лимитов).

**Async/Await:** Эффективная обработка тысяч одновременных чат-сессий и запросов к ИИ без блокировки потоков.


--------------------------------------------------------------------------------

# 2. Основные компоненты и инварианты

Бэкенд разделен на независимые модули, каждый из которых соблюдает свои внутренние законы.

## А. Gateway & Auth (Шлюз и Допуск)

**Задача:** Прием сообщений от Telegram/Web и первичная аутентификация.

**Инвариант Изоляции:** Бэкенд гарантирует, что `auth_id` (Telegram/Email) превращается в `internal_user_id` до того, как данные попадут в бизнес-логику. Ни один бизнес-модуль не знает реальной личности пользователя.

## Б. Normalization Engine (AI-Интеграция)

**Задача:** Взаимодействие с LLM (Gemini/Claude) для превращения текста/голоса в JSON-интенты.

**Инвариант Верификации:** Бэкенд никогда не доверяет ИИ на 100%. Каждый сгенерированный интент проходит через схему валидации (Strong Typing) перед отправкой в БД.

## В. Queue Orchestrator (Диспетчер очередей)

**Задача:** Управление асинхронными задачами через RabbitMQ/NATS.

**Инвариант Порядка:** Гарантирует, что события от блокчейн-сканера и ручной ввод пользователя обрабатываются в правильной последовательности для предотвращения race conditions (состояний гонки).

## Г. DB-Bridge (Мост к PL/pgSQL)

**Задача:** Вызов хранимых процедур и маппинг результатов.

**Инвариант Атомарности:** Бэкенд оборачивает сложные цепочки действий в одну транзакцию БД. Если вызов функции налога упал, Бэкенд гарантирует откат всей операции.


--------------------------------------------------------------------------------

# 3. Жизненный цикл запроса (Request Flow)

**Ingestion:** Получение `webhook` от Telegram.

**Context Loading:** Rust запрашивает у БД текущий активный контекст чата и профиль настроек.

**Inference:** Отправка данных в AI-Агент для определения интентов (Income, Expense, Transfer и т.д.).

**Enforcement:** Вызов соответствующей PL/pgSQL функции (например, `fn_create_transaction`).

**Side Effects:** Запуск воркеров (генерация PDF, пуш-уведомление партнеру по Shared Sovereignty).

**Response:** Возврат пользователю подтверждения через Консильери.


--------------------------------------------------------------------------------

# 4. Спецификация расширяемости

Бэкенд построен по принципу **Trait-based Architecture** (на базе типажей), что позволяет легко добавлять новые функции:

**Custom Adapters:** Легкое добавление новых блокчейнов или банковских агрегаторов (оракулов).

**Plug-and-Play Agents:** Возможность подключать новых ИИ-агентов (например, специализированного налогового консультанта для новой страны) без изменения ядра системы.

**Middleware:** Система перехватчиков, которые могут анализировать трафик на лету для обнаружения аномалий или мошенничества.


--------------------------------------------------------------------------------

# 5. Обработка ошибок: Философия Result

В Бэкенде Sana запрещено использование `panic!`. Каждая ошибка должна быть обработана явно.

**Recoverable Errors:** Если ИИ не понял ввод, Бэкенд возвращает запрос на уточнение в **Pending Layer**.

**Critical Errors:** Если БД вернула нарушение инварианта, Бэкенд логирует детальный технический отчет и выдает пользователю эмпатичное сообщение через **Sana Zen**.


--------------------------------------------------------------------------------

# Итог:

Rust Backend в Sana — это жесткий каркас, который удерживает всю систему вместе. Он не позволяет ошибкам ИИ или сетевым сбоям нарушить математическую чистоту Ledger, обеспечивая при этом плавную и быструю работу интерфейса.
