# 1. Философия: Гибридная модель памяти

Шлюз реализует строгое разделение потоков данных. Мы исходим из того, что сервер Sana не должен знать о личной жизни пользователя, если она не касается финансов.

## 1.1. Поток «Человек-Человек» (Personal Stream)

**Хранение:** Исключительно **Local-First** (SQLite/Realm на устройстве пользователя).

**Роль сервера:** Слепой маршрутизатор (если используется собственный транспорт) или полное неучастие (если поверх Telegram API).

**Доступ Sana:** Нулевой. Сервер не логирует, не анализирует и не сохраняет эти сообщения.

## 1.2. Поток «Человек-Sana» (Cognitive Stream)

**Хранение:** **Server-Side Persistence** (PostgreSQL, таблица `chat_messages`).

**Цель:** Обеспечение «памяти» Агента. Дирижёр должен знать, что вы обсуждали 5 минут назад или месяц назад в рамках проекта.

**Связь с деньгами:** Каждое сообщение получает `message_id`, к которому привязываются транзакции в Ledger. Это создает доказательную базу («Я записала расход, потому что ты прислал это фото»).

# 2. Архитектура обработки (The Dual Pipeline)

Шлюз работает как конечный автомат с двумя состояниями.

## 2.1. Режим «Личное пространство» (Passive Mode)

**Вход:** Сообщение в чате без триггеров.

**Действие Бэкенда:** Игнорирование (Drop packet).

**Лог:** Отсутствует.

## 2.2. Режим «Финансовая сессия» (Active Session)

**Триггер:** Сообщение в ЛС боту, упоминание `@sana` в группе, или ответ (Reply) на сообщение бота.

**Ingestion:** Бэкенд принимает сообщение, выполняет **Identity Injection** (подмена Telegram ID на `internal_user_id`) и направляет в AI-слой.

**Persistence (Фиксация):****Текст:** Сохраняется в `chat_messages` для истории контекста.**Медиа (Чеки/Голос):** Сохраняются во *временное* S3-хранилище, ссылка пишется в `attachment_url`.**Метаданные:** В поле `metadata` записывается, какой агент (`Zen`/`Parser`) обрабатывал запрос.

**Текст:** Сохраняется в `chat_messages` для истории контекста.

**Медиа (Чеки/Голос):** Сохраняются во *временное* S3-хранилище, ссылка пишется в `attachment_url`.

**Метаданные:** В поле `metadata` записывается, какой агент (`Zen`/`Parser`) обрабатывал запрос.

# 3. Политика Zero-Persistence (Нулевой след)

Самый критичный протокол безопасности для работы с сырыми данными.

## 3.1. RAM-only Processing

При получении фото чека или голосового сообщения, обработка происходит исключительно в оперативной памяти процесса `sana-core`. Запрещено сбрасывать сырые байты на диск сервера (кроме транзитного S3).

## 3.2. Мгновенное уничтожение (Immediate Destruction)

Жизненный цикл "сырых" данных:

**Upload:** Фото загружается в S3 (Bucket: `incoming-media`).

**Parse:** Vision Agent извлекает JSON (сумма, дата, товары).

**Cleanup:** Бэкенд **немедленно** отправляет команду `DELETE` в S3 для исходного файла.

**Result:** В базе данных остается только структурированный JSON и очищенный текст. Исходное фото чека уничтожается навсегда.

**Исключение:** Если пользователь явно нажал кнопку "Сохранить фото чека" (для гарантии/налоговой), файл перемещается в защищенный бакет `user-archives` с ключом шифрования пользователя.

## 3.3. Санитария Логов (Log Scrubbing)

Текст сообщений никогда не попадает в системные логи (stdout/Loki).

*Вход:* "Перевод маме 5000".

*Лог:* `[INFO] Intent: Transfer | Payload size: 18b | User: 550e84...`.

# 4. Управление Жизненным Циклом (TTL & Retention)

Бэкенд управляет очисткой таблицы `chat_messages`, чтобы она не превращалась в бесконечный архив мусора.

## 4.1. Эфемерные диалоги (Standard Chat)

**Тип:** Бытовые запросы («Сколько денег?», «Запиши кофе»).

**Политика:** Сообщения хранятся **30 дней** с момента последней активности.

**Cleanup:** Фоновый воркер `sana-cleaner` архивирует или удаляет старые записи, оставляя только связанные транзакции в Ledger.

## 4.2. Связанные диалоги (Entity-Bonded)

**Тип:** Обсуждение конкретного Проекта или Цели (Context ID привязан к `chat_sessions`).

**Политика:** История хранится **пока активен Проект**.

**Логика:** Это позволяет пользователю спустя полгода зайти в проект «Ремонт» и прочитать переписку с Ассистентом о выборе подрядчиков.


--------------------------------------------------------------------------------

# 5. Взаимодействие с Клиентом (Sync Protocol)

Поскольку история хранится в двух местах (локально и на сервере), Бэкенд обеспечивает синхронизацию **только для сообщений Ассистента**.

**Push:** Когда Ассистент отвечает, Бэкенд пушит сообщение (`message_id`, `content`) на устройство через WebSocket/gRPC.

**Local Merge:** Клиентское приложение сохраняет ответ Sana в свою локальную SQLite, формируя единую ленту, где перемешаны личные сообщения (которые сервер не видел) и ответы Sana (которые пришли с сервера).


--------------------------------------------------------------------------------

# 6. Безопасность Данных (Privacy Invariants)

**Identity Split:** В таблице `chat_messages` нет поля `telegram_id`. Есть только `internal_user_id`. Даже при утечке дампа переписки невозможно (без доступа к слою auth) установить авторов сообщений.

**Scope Isolation:** При генерации контекста для ИИ (RAG), Бэкенд выбирает сообщения строго по `session_id` и `internal_user_id`. Перекрестный доступ между пользователями физически невозможен благодаря RLS.


--------------------------------------------------------------------------------

# Резюме

**Ephemeral Messenger Gateway** — это умный фильтр. Он пропускает «сквозь пальцы» личное общение, но цепко сохраняет всё, что касается финансов, при этом уничтожая "улики" (сырые фото/голос) сразу после извлечения пользы.
