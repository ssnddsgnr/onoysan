# 1. Концепция Разрыва Личности (Identity Split)

Фундаментальный принцип архитектуры Sana — техническая изоляция персональных данных от финансовых записей. В системе не существует единой таблицы, где хранились бы и имя пользователя (Telegram ID/Email), и его транзакции.

## 1.1. Двухуровневая модель данных

Система разделена на два изолированных слоя:

### 1. Public Auth Layer (Слой авторизации):

Содержит таблицу `auth_identities`.

Хранит внешние идентификаторы: `telegram_id`, `email`, `apple_id`.

Единственная задача слоя — сопоставить внешний ID с анонимным `internal_user_id`.

### 2. Private Core Layer (Финансовое ядро):

Содержит таблицы `ledger_transactions`, `wallets`, `envelopes`.

Оперирует **исключительно** анонимным `internal_user_id`.

В этом слое физически отсутствуют поля для хранения имен, телефонов или никнеймов. **Результат:** В случае утечки базы данных Ledger злоумышленник получит набор цифр и транзакций, привязанных к случайным UUID, без возможности определить реальных владельцев кошельков.

# 2. Защита персональных данных (PII Protection)

Для персонализации общения (обращение по имени) используются дополнительные меры защиты, исключающие хранение данных в открытом виде рядом с финансами.

**Шифрование покоя (Encryption at Rest):** Имена пользователей и личные настройки хранятся в таблице `users_metadata` только в зашифрованном виде (`encrypted_display_name`). Ключи шифрования отделены от базы данных.

**Санитизация для ИИ (Data Sanitization):** Перед отправкой запроса в LLM (Gemini/Claude) бэкенд автоматически очищает данные от PII (Personal Identifiable Information). В промпт попадает только необходимый контекст, реальные идентификаторы заменяются на системные заглушки.

# 3. Архитектура Нулевого Доверия (Zero Trust)

Ни один компонент системы не доверяет другому по умолчанию. Безопасность обеспечивается на уровне запросов и базы данных.

## 3.1. Санитарный шлюз (Backend Gateway)

Все запросы от клиентских приложений (Telegram, Web) проходят через единый шлюз на Rust.

**Валидация:** Шлюз проверяет подпись запроса и валидность сессии.

**Инъекция ID:** Идентификатор пользователя (`internal_user_id`) никогда не берется из тела запроса (payload) или текста сообщения. Он принудительно подставляется бэкендом из защищенного токена авторизации. Это исключает атаки с подменой ID.

## 3.2. Row Level Security (RLS)

На уровне базы данных PostgreSQL включены политики RLS.

Каждый SQL-запрос автоматически оборачивается в фильтр `WHERE internal_user_id = current_user`.

Даже если в коде приложения будет допущена ошибка (например, пропущен фильтр `WHERE`), база данных физически не вернет строки, не принадлежащие текущему пользователю.

# 4. Управление доступом (Access Control)

Доступ к данным регулируется не только на уровне аккаунта, но и на уровне конкретных сущностей через таблицу `access_grants` (RBAC).

**Домены данных:***User Domain:* Личные данные, доступные только владельцу.*Shared Domain:* Данные (кошелек или проект), к которым выдан доступ другому пользователю (роли: `viewer`, `editor`).

*User Domain:* Личные данные, доступные только владельцу.

*Shared Domain:* Данные (кошелек или проект), к которым выдан доступ другому пользователю (роли: `viewer`, `editor`).

**Принцип наименьших привилегий:** Технические воркеры (например, сканер блокчейна) имеют права `WriteOnly` — они могут записывать новые данные, но не могут читать историю транзакций пользователя.


--------------------------------------------------------------------------------

# 5. Жизненный цикл данных (Data Lifecycle)

Для минимизации рисков утечки внедрены строгие правила хранения временных данных.

**Медиа-файлы:** Фотографии чеков и голосовые сообщения, загруженные в S3, удаляются немедленно после обработки и извлечения из них финансовых данных (JSON).

**Pending Layer TTL:** Черновики неподтвержденных транзакций хранятся ограниченное время (например, 10 дней), после чего удаляются автоматически.


--------------------------------------------------------------------------------

# Резюме

Безопасность Sana строится не на доверии к защищенному периметру, а на математической изоляции данных. Финансы отделены от личности, а доступ к данным жестко ограничен на уровне ядра СУБД, что делает систему устойчивой даже при компрометации внешних интерфейсов.
